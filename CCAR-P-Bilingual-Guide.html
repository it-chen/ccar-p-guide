Introduction

The Claude Certified Architect – Professional certification validates that an individual can design, build, and deliver production-grade AI solutions using Anthropic's Claude platform. It is intended for practitioners working in an architect role who select appropriate models, architectures, and API patterns; apply prompt and context engineering; integrate Claude into enterprise systems; and incorporate evaluation, security, compliance, and governance considerations into their designs.

This guide is the study companion to the official Exam Guide, which is the authoritative reference for the credential: its purpose, intended audience, exam format and content blueprint, scoring, and policies.

Target Candidate

The certification is intended for mid- to senior-level technical professionals who design, build, and deliver production-grade AI solutions using large language models, particularly Claude — primarily solution architects, AI/ML engineers, technical leads, and senior software engineers who operate at the intersection of business requirements and technical implementation.

The exam targets the minimally qualified candidate (MQC): an experienced practitioner who combines an engineering mindset with practical, real-world experience deploying AI solutions. Recommended experience (recommended, not required — there are no mandatory prerequisites):

  • A foundation in software engineering best practices (modular design, separation of concerns, scalability)
  • 3+ years of experience in systems architecture or platform engineering
  • 6+ months of hands-on experience with Claude or comparable LLM-based systems in production
  • Experience delivering end-to-end systems from discovery through deployment and operationalization

1.1 Translate business problems into Claude-based AI solutions

Official wording: "When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • Start from the simplest solution that can work: Anthropic's core guidance is to find the simplest solution possible and only increase complexity when it demonstrably improves outcomes — for many applications, a single optimized LLM call with retrieval and in-context examples is enough, and no agentic system is needed at all.
  • Agentic systems trade latency and cost for better task performance; that trade-off has to make sense for the business problem before any agent pattern is justified.
  • Good candidate problems share traits Anthropic observed in successful deployments (customer support, coding): the task requires both conversation and action, has clear success criteria, enables feedback loops, and integrates meaningful human oversight.
  • Frame the problem in terms of inputs, actions Claude must take through tools, and how success will be measured (e.g., user-defined resolutions in support) before choosing technology.

Key skills:

  • Restate a vague business request as a concrete task with success criteria, required external data/actions, and a human-oversight point.
  • Decide whether the problem needs an LLM call, a workflow, or an agent — and defend the "no agent" answer when a single call suffices.

Official sources: Building effective agents

1.1 将业务问题转化为基于 Claude 的 AI 解决方案

EN: Translate business problems into Claude-based AI solutions

官方原文： "When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

关键知识：

  • 从能跑通的最简单方案开始：Anthropic 的核心指引是找到尽可能简单的方案，只在能明显改善结果时才增加复杂度 —— 对许多应用来说，一次经过优化的 LLM 调用加上检索与上下文示例就足够了，根本不需要智能体（agentic）系统。
  • 智能体系统以延迟和成本换取更好的任务表现；在任何智能体模式被证明合理之前，这个权衡必须对业务问题说得通。
  • 好的候选问题具有 Anthropic 在成功部署（客户支持、编程）中观察到的共同特征：任务既需要对话又需要行动，有明确的成功标准，能形成反馈回路，并整合了有意义的人类监督。
  • 在选技术之前，先用输入、Claude 必须通过工具采取的行动、以及成功如何度量（例如支持场景中由用户定义的解决率）来框定问题。

关键技能：

  • 把一个含糊的业务需求重述为一个具体任务，带上成功标准、所需的外部数据/行动，以及一个人类监督点。
  • 判断该问题需要的是一次 LLM 调用、一个工作流（workflow），还是一个智能体（agent）—— 并在一次调用足够时为「不用智能体」的答案辩护。

官方来源： 构建有效的智能体（Building effective agents）

1.2 Design end-to-end architectures (input → processing → output → feedback loops)

Official wording: "The basic building block of agentic systems is an LLM enhanced with augmentations such as retrieval, tools, and memory." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • The basic building block is the augmented LLM: an LLM enhanced with retrieval, tools, and memory, which can generate its own search queries, select tools, and decide what information to retain. End-to-end designs compose this block.
  • A complete design covers the full loop: input handling, the processing pattern (one or more LLM calls, tool calls, retrieval), output formatting/validation, and a feedback path — tool results and code execution give the agent "ground truth" at each step to assess progress.
  • Feedback loops appear at several levels: programmatic gates between chained steps, evaluator feedback in evaluator-optimizer loops, test results for coding agents, and human feedback at checkpoints or blockers.
  • Agents need explicit stopping conditions (completion, or limits such as a maximum number of iterations) to maintain control; transparency — explicitly showing the agent's planning steps — is one of Anthropic's three core implementation principles, alongside simplicity and a carefully crafted agent-computer interface (ACI).

Key skills:

  • Sketch an architecture as input → processing → output → feedback, naming where retrieval, tools, memory, and human checkpoints sit.
  • Place programmatic checks (gates) between steps so a failing intermediate result stops or reroutes the flow instead of propagating.

Official sources: Building effective agents

1.2 设计端到端架构（输入 → 处理 → 输出 → 反馈回路）

EN: Design end-to-end architectures (input → processing → output → feedback loops)

官方原文： "The basic building block of agentic systems is an LLM enhanced with augmentations such as retrieval, tools, and memory." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

关键知识：

  • 基本构件是增强型 LLM（augmented LLM）：一个被检索、工具与记忆增强的 LLM，它能生成自己的搜索查询、选择工具，并决定保留哪些信息。端到端设计就是由这个构件组合而成的。
  • 一个完整的设计覆盖整个回路：输入处理、处理模式（一次或多次 LLM 调用、工具调用、检索）、输出格式化/校验，以及一条反馈路径 —— 工具结果与代码执行在每一步为智能体提供「事实依据（ground truth）」来评估进展。
  • 反馈回路出现在多个层面：链式步骤之间的程序化关卡（gates）、评估者-优化者回路（evaluator-optimizer loops）中的评估者反馈、编程智能体的测试结果，以及检查点或阻塞点处的人类反馈。
  • 智能体需要明确的停止条件（完成，或诸如最大迭代次数之类的限制）以保持可控；透明性 —— 明确展示智能体的规划步骤 —— 是 Anthropic 三大核心实现原则之一，另外两个是简单性与精心设计的智能体-计算机接口（agent-computer interface，ACI）。

关键技能：

  • 把架构画成输入 → 处理 → 输出 → 反馈，并标明检索、工具、记忆与人类检查点的位置。
  • 在步骤之间放置程序化检查（关卡），使失败的中间结果能停止或改道流程，而不是继续向后传播。

官方来源： 构建有效的智能体（Building effective agents）

1.3 Select appropriate architectural patterns (workflow, agentic, augmented LLM)

Official wording: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. … Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • Anthropic's central distinction: workflows are systems where LLMs and tools are orchestrated through predefined code paths; agents are systems where LLMs dynamically direct their own processes and tool usage. Both are "agentic systems."
  • The five workflow patterns: prompt chaining (fixed sequence, each call processes the previous output; use when a task decomposes cleanly into fixed subtasks — trades latency for accuracy), routing (classify input, direct it to a specialized follow-up; also used to send easy questions to smaller models and hard ones to more capable models), parallelization (sectioning — independent subtasks in parallel; voting — the same task run multiple times for confidence), orchestrator-workers (a central LLM dynamically breaks down the task, delegates to workers, and synthesizes results; use when subtasks can't be predicted in advance), and evaluator-optimizer (one call generates, another evaluates and feeds back in a loop; use when clear evaluation criteria exist and iterative refinement measurably helps).
  • Choose a true agent only for open-ended problems where the number of steps can't be predicted and no fixed path can be hardcoded — accepting higher cost and the risk of compounding errors, mitigated by sandbox testing and guardrails.
  • Patterns are not prescriptive: they can be shaped and combined, and complexity should be added only when measurement shows it improves outcomes.

Key skills:

  • Given a scenario stem, name the pattern and the deciding feature (fixed steps → chaining; distinct input categories → routing; unpredictable subtasks → orchestrator-workers or an agent; clear quality criteria + iteration → evaluator-optimizer).
  • Reject over-engineering distractors: a multi-agent design offered for a fixed, predictable process is the classic wrong answer.

Official sources: Building effective agents

1.3 选择合适的架构模式（工作流、智能体、增强型 LLM）

EN: Select appropriate architectural patterns (workflow, agentic, augmented LLM)

官方原文： "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. … Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

关键知识：

  • Anthropic 的核心区分：工作流（workflows）是 LLM 与工具通过预定义代码路径编排的系统；智能体（agents）是 LLM 动态主导自身流程与工具使用的系统。两者都属于「智能体系统（agentic systems）」。
  • 五种工作流模式：提示链（prompt chaining）（固定序列，每次调用处理上一次的输出；适用于任务能干净地分解为固定子任务的场合 —— 以延迟换准确性）、路由（routing）（对输入分类，导向专门的后续处理；也用于把简单问题发给更小的模型、难题发给能力更强的模型）、并行化（parallelization）（分段 sectioning —— 独立子任务并行执行；投票 voting —— 同一任务多次运行以获得置信度）、编排者-工作者（orchestrator-workers）（一个中央 LLM 动态拆解任务、委派给工作者并综合结果；适用于子任务无法预先预测的场合）、评估者-优化者（evaluator-optimizer）（一次调用生成，另一次调用评估并反馈，循环进行；适用于有明确评估标准且迭代改进确有帮助的场合）。
  • 只对开放式问题选择真正的智能体：步骤数无法预测、固定路径无法硬编码 —— 同时接受更高的成本与错误累积的风险，用沙箱测试与护栏（guardrails）来缓解。
  • 这些模式不是硬性规定：它们可以塑形与组合，复杂度只应在测量表明能改善结果时才增加。

关键技能：

  • 给定一个场景题干，说出模式名称与决定性特征（步骤固定 → 链式；输入类别分明 → 路由；子任务不可预测 → 编排者-工作者或智能体；质量标准明确 + 迭代 → 评估者-优化者）。
  • 拒绝过度工程的干扰项：为固定、可预测的流程提供多智能体设计，是经典的错误答案。

官方来源： 构建有效的智能体（Building effective agents）

1.4 Design multi-agent systems and orchestration strategies

Official wording: "Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." — How we built our multi-agent research system, Anthropic (https://www.anthropic.com/research/multi-agent-research-system)

Key knowledge:

  • Anthropic's production Research system uses the orchestrator-worker pattern: a lead agent analyzes the query, develops a strategy, and spawns specialized subagents that explore different aspects in parallel; the lead then synthesizes their results.
  • Subagents facilitate compression: each works in its own context window and condenses the most important tokens for the lead agent, instead of one agent accumulating everything it reads. Each subagent also provides separation of concerns — distinct tools, prompts, and exploration trajectories.
  • In the Agent SDK, subagents are separate agent instances the main agent spawns for focused subtasks: intermediate tool calls and results stay inside the subagent, and only its final message returns to the parent. A subagent's context starts fresh — it does not receive the parent's conversation history, so everything it needs must be in the delegation prompt.
  • Orchestration is a prompting problem as much as an architecture one: the lead agent must be taught how to delegate — decomposing the query into subtasks and describing each one in detail (objective, output format, tool/source guidance, clear task boundaries). Early failures Anthropic observed included spawning far too many subagents for simple queries and agents distracting each other with excessive updates.
  • Multi-agent is not free: coordination complexity grows rapidly and token consumption is far higher than a single agent, so it fits problems that are genuinely parallel and open-ended — not tasks with shared state or heavy interdependencies.

Key skills:

  • Design a delegation brief for a subagent: objective, output format, tools/sources to use, and explicit boundaries.
  • Choose per-subagent configuration deliberately — specialized system prompt, restricted tool set, and a model override (e.g., a cheaper/faster model for exploration, a stronger model for synthesis).
  • Argue against multi-agent when subtasks are sequential, tightly coupled, or predictable — and propose a workflow instead.

Official sources: How we built our multi-agent research system · Subagents in the SDK · Building effective agents

1.4 设计多智能体系统与编排策略

EN: Design multi-agent systems and orchestration strategies

官方原文： "Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." — How we built our multi-agent research system, Anthropic (https://www.anthropic.com/research/multi-agent-research-system)

关键知识：

  • Anthropic 的生产级 Research 系统使用编排者-工作者模式：一个主智能体（lead agent）分析查询、制定策略，并派生出专门的子智能体（subagents）并行探索不同方面；主智能体随后综合它们的结果。
  • 子智能体有助于压缩：每个子智能体在自己的上下文窗口中工作，把最重要的 token 提炼后交给主智能体，而不是让一个智能体累积它读过的一切。每个子智能体还提供关注点分离 —— 不同的工具、提示与探索轨迹。
  • 在 Agent SDK 中，子智能体是主智能体为聚焦的子任务派生的独立智能体实例：中间的工具调用与结果留在子智能体内部，只有它的最终消息返回给父级。子智能体的上下文是全新开始的 —— 它收不到父级的对话历史，因此它需要的一切都必须写在委派提示里。
  • 编排既是架构问题，也是提示问题：必须教会主智能体如何委派 —— 把查询分解为子任务，并详细描述每一个（目标、输出格式、工具/来源指引、清晰的任务边界）。Anthropic 早期观察到的失败包括：为简单查询派生过多子智能体，以及智能体之间用过多的更新互相干扰。
  • 多智能体不是免费的：协调复杂度增长很快，token 消耗远高于单个智能体，因此它适合真正可并行、开放式的问题 —— 不适合有共享状态或强相互依赖的任务。

关键技能：

  • 为子智能体设计一份委派简报：目标、输出格式、要使用的工具/来源，以及明确的边界。
  • 有意识地为每个子智能体选择配置 —— 专门的系统提示、受限的工具集，以及模型覆盖（例如用更便宜/更快的模型做探索、用更强的模型做综合）。
  • 在子任务是顺序的、紧密耦合的或可预测的时候，反对使用多智能体 —— 并改为提出工作流方案。

1.5 Apply decomposition techniques for complex problem solving

Official wording: "Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • Decomposition is pattern-specific: prompt chaining decomposes a task into a fixed sequence of easier steps (each LLM call gets an easier task, which is why chaining trades latency for accuracy); parallelization decomposes into independent subtasks (sectioning); orchestrator-workers and multi-agent systems decompose dynamically, with the lead/orchestrator deciding the subtasks from the specific input.
  • In multi-agent designs, the lead agent's first job is decomposition: it analyzes the query, develops a strategy, and only then spawns workers — and it saves its plan to memory so the plan survives if the context window fills and is truncated.
  • Good decomposition gives each unit one focused concern: a separate LLM call per consideration generally performs better than one call juggling all considerations at once, and subagents return distilled results rather than raw exploration.
  • Decomposition has a failure mode in both directions: too coarse (one agent drowning in a huge, mixed task) and too fine (dozens of subagents for a simple query, coordination overhead, agents duplicating or distracting each other).

Key skills:

  • Decompose a complex task two ways — as a fixed chain and as dynamically delegated subtasks — and pick based on whether the subtasks are predictable.
  • Write subtask definitions that are self-contained: a worker with a fresh context must be able to act without seeing the parent conversation.

1.5 运用分解技术解决复杂问题

1.6 Align solutions to business value pillars (efficiency, transformation, productivity, cost, performance SLAs)

Official wording: "Agentic systems often trade latency and cost for better task performance, and you should consider when this tradeoff makes sense." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • Every pattern choice is a value trade-off stated in the official guidance: agentic systems trade latency and cost for task performance; prompt chaining trades latency for accuracy; a more capable model can lower cost-per-task by finishing in fewer turns and less thinking time, even at a higher price per token.
  • Value must be measurable to be claimed: successful deployments Anthropic cites have clear success criteria (e.g., support resolutions) — to the point that some vendors price per successful resolution. "Measure performance and iterate" is the stated key to success when combining patterns.
  • Routing is a value lever, not just an architecture lever: sending easy/common requests to a fast, low-cost model and hard/unusual ones to a more capable model optimizes the cost/performance mix for the whole workload.
  • Multi-agent designs must clear a higher value bar: Anthropic's Research system substantially outperformed a single agent on its internal research eval, but at much higher token cost — the pattern is justified for high-value, parallelizable tasks, not as a default.

Key skills:

  • For a proposed design, state the trade explicitly: what is gained (accuracy, capability, throughput), what is paid (latency, tokens, coordination), and which business metric proves it was worth it.
  • Spot the SLA-breaking distractor: the most autonomous or most capable option offered where a latency or cost constraint in the stem rules it out.

2.1 Select appropriate Claude models based on trade-offs

Official wording: "If you're unsure which model to use, start with Claude Opus 5.5 for most workloads. Key knowledge:

  • The model family is a trade-off ladder between intelligence, speed, and cost: the Opus class delivers the highest intelligence for complex reasoning and long, multi-step work at higher cost and latency; Sonnet is the balanced tier — strong intelligence with faster, cheaper operation for most practical applications; Haiku is the fastest, lowest-cost class, built for high-volume, latency-sensitive work such as classification, extraction, and routing. Starting too small also makes it hard to distinguish model failures from setup failures.

  • Selection inputs beyond raw capability: context window size, maximum output, and thinking configuration (adaptive thinking / effort) all differ by model and belong in the trade-off.

Key skills:

  • Map a workload to a tier from the stem's signals: "real-time, high-volume, simple" → Haiku class; "complex reasoning, long autonomous work" → Opus class; "general production default" → Sonnet class — then justify with the cost-per-task argument.
  • Propose a mixed-model design (route or delegate by difficulty) instead of a single-model answer when the workload has mixed difficulty.

2.2 Design system prompts, templates, and guardrails

Official wording: "The optimal altitude strikes a balance: specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics to guide behavior." — Effective context engineering for AI agents, Anthropic (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Key knowledge:

  • The system prompt sets Claude's role, behavior, and constraints for the whole interaction; setting a role in the system prompt focuses behavior and tone, and even a single sentence makes a difference.
  • Write instructions as if for "a brilliant but new employee" who lacks context on your norms: be clear, direct, and specific about the desired output, format, and constraints; give sequential steps as numbered lists or bullets when order or completeness matters; and add the context/motivation behind an instruction, because Claude can generalize from the explanation.
  • Structure complex prompts with XML tags — separate <instructions>, <context>, <input>, and <example> sections with consistent, descriptive tag names (nesting where content is hierarchical) so Claude parses each part unambiguously.
  • Guardrails are partly a prompt-design task and partly an architecture task: a separate model call screening inputs/outputs (parallelization as guardrails) tends to perform better than one call handling both the guardrail and the core response; and prompt-level instructions are guidance, not enforcement — hard constraints belong in code around the model (validation, tool restrictions, gates), a distinction the exam tests repeatedly.
  • System prompts should be written "at the right altitude" (from the context-engineering guidance): specific enough to guide behavior effectively, flexible enough to leave the model strong heuristics — neither brittle hardcoded logic nor vague guidance that assumes shared context. Organize them into distinct sections (background, instructions, tool guidance, output format).

Key skills:

  • Draft a system-prompt skeleton: role → task and constraints → tool/behavior rules → output format, each in its own labeled section.
  • For a stated safety or compliance requirement, decide what goes in the prompt (behavioral guidance) versus what must be enforced outside it (screening call, tool allow-list, programmatic check).

  • 起草一个系统提示骨架：角色 → 任务与约束 → 工具/行为规则 → 输出格式，每部分各自独立成节并标注。

2.3 Apply prompt engineering techniques (zero-shot, few-shot, chain-of-thought)

Official wording: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure. A few well-crafted examples (known as few-shot or multishot prompting) improve accuracy and consistency." — Prompting best practices, Anthropic (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

Key knowledge:

  • Zero-shot is the baseline: a clear, direct instruction with no examples. Improve it first with specificity, context/motivation, and structure before adding techniques.
  • Few-shot (multishot) prompting: examples are one of the most reliable ways to steer output format, tone, and structure and to improve accuracy and consistency. Make examples relevant (mirror the real use case), diverse (cover edge cases, varied enough that Claude doesn't pick up unintended patterns), and structured (each in <example> tags, the set in <examples>).
  • Chain-of-thought / thinking: for complex multistep reasoning and reflection after tool use, guide Claude to think before answering. Current models offer adaptive thinking, where Claude dynamically decides when and how much to think, calibrated by the effort parameter and query complexity; higher effort elicits more thinking, and on easy queries the model may respond directly. Older models use manual extended thinking with a token budget.
  • Thinking is a cost/latency lever, not a free upgrade: over-thinking inflates thinking tokens and slows responses, so constrain it with instructions or a lower effort setting when the task doesn't need depth; if a hard ceiling on thinking cost is required, control it through effort / max_tokens per the model's configuration.
  • Tell Claude what to do instead of what not to do when steering output format, and match the prompt's own style to the output style you want.

Key skills:

  • Choose the lightest technique that fits the failure: inconsistent format → few-shot examples; wrong reasoning on multistep problems → guided thinking; vague output → clearer zero-shot instruction with context.
  • Write a few-shot set that is relevant, diverse, and XML-structured — and recognize a bad set (near-duplicate examples that teach an unintended pattern) in a scenario stem.

2.3 运用提示工程技术（零样本、少样本、思维链）

EN: Apply prompt engineering techniques (zero-shot, few-shot, chain-of-thought)

官方原文： "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure. A few well-crafted examples (known as few-shot or multishot prompting) improve accuracy and consistency." — Prompting best practices, Anthropic (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

关键知识：

  • 零样本（Zero-shot）是基线：一条清晰、直接、没有任何示例的指令。先用具体性、背景/动机与结构来改进它，然后再添加其他技术。
  • 少样本（Few-shot / multishot）提示：示例是引导输出格式、语气与结构、提高准确性与一致性的最可靠方法之一。让示例具有相关性（镜像真实用例）、多样性（覆盖边缘情况，变化足够多，使 Claude 不会学到非预期的模式）与结构性（每个示例放在 <example> 标签中，整组放在 <examples> 中）。
  • 思维链 / 思考（Chain-of-thought / thinking）：对复杂的多步推理以及工具使用后的反思，引导 Claude 先思考再回答。当前模型提供自适应思考（adaptive thinking），Claude 会动态决定何时思考、思考多少，由 effort 参数与查询复杂度校准；effort 越高引发的思考越多，在简单查询上模型可能直接回答。较旧的模型使用带 token 预算的手动扩展思考（extended thinking）。
  • 思考是成本/延迟杠杆，不是免费升级：过度思考会膨胀思考 token 并拖慢响应，因此当任务不需要深度时，用指令或更低的 effort 设置来约束它；如果对思考成本有硬上限要求，按模型配置通过 effort / max_tokens 来控制。
  • 在引导输出格式时，告诉 Claude 该做什么，而不是不该做什么，并让提示自身的风格与你想要的输出风格一致。

关键技能：

  • 选择与故障匹配的最轻技术：格式不一致 → 少样本示例；多步问题推理错误 → 引导思考；输出含糊 → 带背景的更清晰的零样本指令。
  • 写出一组相关、多样、XML 结构化的少样本示例 —— 并能在场景题干中识别出一组坏示例（近乎重复、教会了非预期模式的示例）。

2.4 Optimize context windows and manage token usage

Official wording: "Context engineering refers to the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference, including all the other information that may land there outside of the prompts." — Effective context engineering for AI agents, Anthropic (https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Key knowledge:

  • Context engineering is "the natural progression of prompt engineering": curating and maintaining the optimal set of tokens during inference — system instructions, tools, MCP data, external data, and message history — not just the wording of one prompt.
  • The context window is a finite attention budget: as the number of tokens grows, the model's ability to accurately recall information from context decreases — a gradual degradation the docs call context rot, not a hard cliff. Everything counts toward the window: system prompt, all messages including tool results, images and documents, tool definitions, and the output (including thinking tokens) the model generates.
  • The guiding principle: find the smallest possible set of high-signal tokens that maximizes the likelihood of the desired outcome. More context is not automatically better.
  • Practical management strategies from the official guidance: just-in-time retrieval (keep lightweight identifiers — file paths, stored queries, links — and load data dynamically at runtime instead of pre-processing everything into context up front); compaction/summarization for long-running conversations (server-side compaction is the primary strategy the context-windows docs point to); subagents as context isolation, so exploration happens in a separate window and only a distilled result returns; and long-context prompt structure — long documents placed above the query, documents wrapped in XML tags with metadata, and asking Claude to quote relevant passages before answering (most relevant at 20k+ tokens).
  • Measure before optimizing: responses report consumption in the usage field, and the token counting API can estimate a request before sending it.

Key skills:

  • Diagnose a "model got worse over a long session" scenario as context rot / bloated context, and prescribe curation (trim, summarize, just-in-time loading, subagent offload) rather than a model swap.
  • Budget a request: account for system prompt, tool definitions, history, retrieved data, and reserved output/thinking tokens against the model's window.

关键知识：

  • 上下文工程是「提示工程的自然演进」：在推理期间策划并维护一组最优的 token —— 系统指令、工具、MCP 数据、外部数据与消息历史 —— 而不只是一个提示的措辞。
  • 上下文窗口是一种有限的注意力预算（attention budget）：随着 token 数量增长，模型从上下文中准确回忆信息的能力会下降 —— 文档称之为上下文腐化（context rot），是一种渐进的退化，不是硬性的悬崖。所有东西都计入窗口：系统提示、包括工具结果在内的全部消息、图像与文档、工具定义，以及模型生成的输出（包括思考 token）。
  • 指导原则：找到能最大化期望结果可能性的、最小的高信号 token 集合。上下文更多并不自动更好。
  • 来自官方指引的实用管理策略：即时检索（just-in-time retrieval）（保留轻量标识符 —— 文件路径、已存查询、链接 —— 在运行时动态加载数据，而不是预先把一切都处理进上下文）；为长时运行的对话做压缩/摘要（服务端压缩 compaction 是上下文窗口文档指出的主要策略）；把子智能体用作上下文隔离，使探索在单独的窗口中发生、只返回提炼后的结果；以及长上下文提示结构 —— 把长文档放在查询上方、文档用带元数据的 XML 标签包裹，并要求 Claude 在回答前引用相关段落（在 20k+ token 时最相关）。
  • 先度量再优化：响应在 usage 字段中报告消耗，token 计数 API 可以在发送前估算一个请求。

关键技能：

  • 把「模型在长会话中变差了」的场景诊断为上下文腐化 / 上下文膨胀，并开出处方：策划（裁剪、摘要、即时加载、卸载给子智能体），而不是换模型。
  • 为一个请求做预算：对照模型的窗口，核算系统提示、工具定义、历史、检索数据，以及预留的输出/思考 token。

官方来源： 为 AI 智能体做有效的上下文工程（Effective context engineering for AI agents） · 上下文窗口（Context windows） · 提示最佳实践（Prompting best practices）

2.5 Implement prompt reuse strategies (caching, modular prompts, Skills)

Official wording: "Prompt caching optimizes your API usage by letting the API resume from specific prefixes in your prompts. … Prompt caching covers the full prefix: tools, system, and messages (in that order), up to and including the block designated with cache_control." — Prompt caching, Anthropic (https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Key knowledge:

  • Prompt caching lets the API resume from a specific prompt prefix instead of reprocessing it. It covers the full prefix in order — tools, then system, then messages — up to and including the block marked with cache_control. Two modes: automatic caching (one top-level cache_control field; best for growing multi-turn conversations) and explicit cache breakpoints on individual content blocks for fine-grained control.
  • Cache mechanics that exam stems probe: the default lifetime is 5 minutes, refreshed at no additional cost each time the cached content is used (a 1-hour duration is available at additional cost); the cached prefix must match exactly — any change to content inside the prefix invalidates reuse, so stable content goes first and dynamic content (user input, timestamps) goes after the breakpoint; and prompts below a minimum size cannot be cached.
  • Design prompts modularly so reuse is possible: a stable, shared prefix (system prompt, tool definitions, few-shot examples, reference documents) separated from the per-request variable tail. This static/dynamic split is the same idea as the system-prompt altitude/section guidance in 2.2.
  • Agent Skills are the other reuse mechanism: reusable, filesystem-based resources — a directory with a SKILL.md (YAML frontmatter plus instructions), optionally bundled with code and reference files — that package workflows, context, and best practices so a general-purpose agent acts as a specialist. Skills reuse through progressive disclosure: only the name and description metadata (~100 tokens per Skill) are always loaded; the SKILL.md instructions load when a request matches the description; bundled resources and code load only as needed — so many Skills can be installed without a standing context penalty.

Key skills:

  • Place a cache breakpoint correctly in a described request: after the last stable block, before the first per-request content — and predict the miss when a stem inserts a timestamp or user-specific text inside the prefix.
  • Choose the reuse mechanism by what is being reused: identical prompt prefix across calls → caching; a repeatable procedure/domain know-how across tasks → a Skill; a one-off instruction → neither.

关键技能：

  • 在一个描述的请求中正确放置缓存断点：在最后一个稳定块之后、第一个每请求内容之前 —— 并能预测当题干在前缀内插入时间戳或用户专属文本时的缓存未命中。

3.1 Evaluate tool/agent configuration for capability bloat

Official wording: "Tools are a new kind of software which reflects a contract between deterministic systems and non-deterministic agents. More tools don’t always lead to better outcomes." — Writing effective tools for AI agents, Anthropic (https://www.anthropic.com/research/writing-tools-for-agents)

Key knowledge:

  • A tool is a contract between a deterministic system and a non-deterministic agent; tools must be designed for agents, not copied from developer-facing APIs.
  • More tools is not better: every tool definition consumes context, and overlapping or rarely used tools make tool selection harder and less reliable. Anthropic's first principle is choosing the right tools to implement — and not to implement.
  • Namespacing groups related tools under clear prefixes and defines boundaries in functionality, so the agent (and the operator) can see which capability area a tool belongs to.
  • Tool responses should return meaningful, high-signal context and be optimized for token efficiency; raw, oversized dumps waste context and degrade downstream reasoning.
  • The MCP connector supports scoping exposure per server: enable all tools, allowlist specific tools, or denylist unwanted tools, with per-tool configuration — the platform-level lever for cutting bloat without changing the server.

Key skills:

  • Audit a tool set for overlap, dead tools, and tools the task never needs; remove or allowlist rather than adding instructions to "ignore" them.
  • Consolidate several narrow calls into one tool that matches how the agent actually works, and namespace what remains.
  • Measure the effect: run tool-use evaluations before and after pruning, instead of judging by intuition.

3.2 Analyze authentication and authorization requirements to identify security gaps

Official wording: "The Model Context Protocol provides authorization capabilities at the transport level, enabling MCP clients to make requests to restricted MCP servers on behalf of resource owners. Authorization is OPTIONAL for MCP implementations." — Authorization - Model Context Protocol, Anthropic (https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)

Key knowledge:

  • In the MCP specification, authorization is transport-level and optional: HTTP-based transports should follow the OAuth-based authorization specification; stdio transports should not, and instead retrieve credentials from the environment.
  • MCP authorization is built on OAuth 2.1, OAuth 2.0 Authorization Server Metadata (RFC 8414), and Dynamic Client Registration (RFC 7591). PKCE is required for all clients.
  • Grant type follows who is acting: authorization code when the client acts on behalf of a human end user; client credentials when the client is another application and no user is impersonated.
  • Token handling rules are concrete gap checks: tokens only in the Authorization header (never in the URI query string), on every HTTP request; servers must validate tokens and return 401 for invalid or expired ones, 403 for insufficient scopes.
  • Standing requirements: HTTPS everywhere, validated redirect URIs (localhost or HTTPS only), secure token storage, and enforced token expiration and rotation.

Key skills:

  • Map each integration to its actor (end user vs. service) and flag mismatches — e.g., a shared static API key where per-user OAuth is required, or a user token being used for a machine-to-machine call.
  • Check a server configuration against the spec checklist: metadata discovery, PKCE, audience/scope validation, token lifetime, and whether least-privilege scopes match what each tool actually does.
  • Distinguish authentication (who is calling) from authorization (what this token may do) when locating a gap; most exam traps hide an authorization gap behind working authentication.

Official sources: MCP Authorization specification · MCP Authorization Security Considerations · MCP connector (OAuth authentication)

  • 在定位缺口时区分认证（authentication，谁在调用）与授权（authorization，这个 token 能做什么）；大多数考试陷阱把授权缺口藏在能正常工作的认证背后。

3.3 Evaluate accuracy-latency trade-offs and justify configuration decisions

Official wording: "Cost and intelligence are usually pictured as a frontier where one buys the other. The first group of levers on this page moves a workload toward that frontier by cutting cost without touching quality; only the second group moves along it." — Optimizing for cost and intelligence, Anthropic (https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)

Key knowledge:

  • Cost, latency, and intelligence form one frontier: some levers cut cost without touching quality ("free wins" such as prompt caching and batch processing), while others deliberately trade intelligence for cost or speed (model choice, effort, output caps).
  • Latency has two different sources: per-request processing (reduced by caching repeated prefixes, which also cuts cost) and scheduling delay (the Message Batches API trades immediacy for a 50% price reduction — most batches finish in under an hour, with results available by 24 hours at the latest).
  • Streaming, model tier, and context size are configuration decisions with measurable accuracy and latency consequences; none of them is "always max out."
  • A justification is only defensible if it is measured on your own workload: Anthropic's published figures are directional, and the docs prescribe measuring the lever on your traffic before adopting it.

Key skills:

  • Classify a workload first — interactive (a person is waiting) vs. asynchronous — then pick the mechanism: synchronous + caching for interactive, batches for delay-tolerant volume.
  • State a trade-off decision in exam form: the constraint (latency budget / accuracy floor), the lever chosen, and the metric that proves it holds.
  • Reject false fixes: a bigger context window does not fix slow retrieval, and a stronger model does not fix a latency problem caused by resending an uncached prefix.

3.4 Analyze observability challenges and select monitoring strategies at scale

Official wording: "A transcript (also called a trace or trajectory) is the complete record of a trial, including outputs, tool calls, reasoning, intermediate results, and any other interactions." — Demystifying evals for AI agents, Anthropic (https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Key knowledge:

  • Agents are hard to observe because behavior emerges over many turns: tool calls, state changes, and intermediate results — errors can propagate and compound before the final answer looks wrong.
  • The unit of observability is the transcript (trace/trajectory): the complete record of a trial, including outputs, tool calls, reasoning, and intermediate results; for the Anthropic API this is the full messages array. The outcome — the final state in the environment — must be checked separately from what the agent claims.
  • Every API response carries a usage block (uncached input, cache creation, cache read, and output tokens), which is the per-request raw material for cost and token monitoring; cache fields are how you verify caching is actually working.
  • Prompt caching has its own silent failure mode worth monitoring: a breakpoint placed on content that changes every request produces cache writes on every request and never a read — visible only in the cache token counts.

Key skills:

  • Instrument at three levels: per-request usage/latency, per-trial transcripts for sampled or failed runs, and outcome checks against the real system of record.
  • Define alerts on the signals that precede user complaints: error and refusal rates, cache-read ratio, tokens per task, and tool-call failure rates — segmented by model and tool, not just global averages.
  • Keep transcripts reviewable: when a failure is found in production, the trace should be convertible into an eval task (this is the bridge to Domain 4).

This method can reduce the number of failed retrievals by 49% and, when combined with reranking, by 67%." — Contextual Retrieval, Anthropic (https://www.anthropic.com/research/contextual-retrieval)

Key knowledge:

  • The standard RAG pipeline: split the corpus into chunks (usually no more than a few hundred tokens), embed the chunks into vectors, store them in a vector database, and at query time retrieve the most relevant chunks and append them to the prompt.
  • Traditional RAG's core weakness is that chunking strips context: a chunk that says "revenue grew 3%" is unfindable if the company and quarter lived elsewhere in the document.
  • Contextual Retrieval fixes this by prepending chunk-specific explanatory context before embedding and before BM25 indexing, producing Contextual Embeddings and Contextual BM25; Anthropic measured 49% fewer failed retrievals, and 67% fewer when combined with reranking.
  • Prompt caching makes contextualization cheap to generate at scale, and also powers the alternative: for a knowledge base under ~200,000 tokens, skip RAG entirely and put the whole corpus in a cached prompt.
  • Indexing is hybrid by default in the official recipe: build both the semantic (embedding) index and the lexical (BM25/TF-IDF) index over the same contextualized chunks.

Key skills:

  • Size the solution before building it: small, stable corpus → cached long prompt; large or fast-changing corpus → indexed RAG.
  • Choose chunk boundaries that keep a unit of meaning intact, then add generated context to each chunk before indexing — and evaluate retrieval (failed-retrieval rate / recall) separately from answer quality.
  • Add reranking when the accuracy requirement justifies the extra latency and cost, and justify it with the measured retrieval improvement.

Official sources: Contextual Retrieval · Anthropic Cookbook (Contextual Retrieval implementation)

3.5 设计带恰当分块与索引策略的 RAG 管线

EN: Design a RAG pipeline with appropriate chunking and indexing strategies

官方原文： "Contextual Retrieval solves this problem by prepending chunk-specific explanatory context to each chunk before embedding (“Contextual Embeddings”) and creating the BM25 index (“Contextual BM25”). This method can reduce the number of failed retrievals by 49% and, when combined with reranking, by 67%." — Contextual Retrieval, Anthropic (https://www.anthropic.com/research/contextual-retrieval)

关键知识：

  • 标准的 RAG 管线：把语料切成块（chunks，通常不超过几百个 token），把块嵌入（embed）成向量，存入向量数据库，查询时检索最相关的块并追加到提示中。
  • 传统 RAG 的核心弱点是分块会剥离上下文：一个写着「收入增长 3%」的块，如果公司与季度在文档的其他地方，就找不到。
  • 上下文化检索（Contextual Retrieval）通过在嵌入之前、以及在 BM25 索引之前，为每个块前置块专属的解释性上下文来修复这一点，产出上下文化嵌入（Contextual Embeddings）与上下文化 BM25（Contextual BM25）；Anthropic 测得检索失败减少 49%，与重排序（reranking）结合时减少 67%。
  • 提示缓存使大规模生成上下文化内容变得便宜，它还支撑了另一种方案：对一个小于约 200,000 token 的知识库，完全跳过 RAG，把整个语料放进一个缓存的提示里。
  • 官方配方的索引默认是混合的：在同一批上下文化块上同时构建语义（嵌入）索引与词法（BM25/TF-IDF）索引。

关键技能：

  • 在动手构建之前先定方案规模：小而稳定的语料 → 缓存的长提示；大或变化快的语料 → 索引化 RAG。
  • 选择能保持意义单元完整的分块边界，然后在索引前为每个块添加生成的上下文 —— 并把检索（检索失败率 / 召回率）与答案质量分开评估。
  • 当准确性要求能证明额外的延迟与成本合理时添加重排序，并用测得的检索改进来为它辩护。

3.6 Apply retrieval strategies matched to data shape and query pattern

Official wording: "While embedding models excel at capturing semantic relationships, they can miss crucial exact matches. BM25 is a ranking function that uses lexical matching to find precise word or phrase matches. It's particularly effective for queries that include unique identifiers or technical terms." — Contextual Retrieval, Anthropic (https://www.anthropic.com/research/contextual-retrieval)

Key knowledge:

  • Embeddings and BM25 fail in opposite directions: semantic search misses exact terms (identifiers, codes, rare names); lexical search misses paraphrase and meaning. Combining both with rank fusion covers both failure modes.
  • Query pattern decides the mix: exact-match lookups (error codes, SKUs, clause numbers) lean lexical; natural-language questions lean semantic; most production systems need the hybrid.
  • Data shape decides the unit: prose documents → contextualized text chunks; codebases → symbol/function-level chunks with file context; frequently updated data → the index freshness and re-indexing path matters as much as the ranking.
  • Retrieval is not always the answer: direct long-context inclusion (with caching) beats retrieval when the corpus fits, and agentic search over a filesystem can beat a vector index for structured, navigable data.

Key skills:

  • Diagnose a retrieval failure before fixing it: was the right chunk never indexed, indexed but not ranked in top-K, or retrieved but ignored? Each has a different fix.
  • Match strategy to a described workload in one step: state data shape + query pattern → chosen strategy (lexical / semantic / hybrid / no-RAG) with the reason.
  • Tune top-K and reranking against a retrieval metric, not by feel — more chunks is not free: it costs tokens and can bury the answer.

Official sources: Contextual Retrieval · Effective context engineering for AI agents

3.6 运用与数据形态和查询模式匹配的检索策略

EN: Apply retrieval strategies matched to data shape and query pattern

官方原文： "While embedding models excel at capturing semantic relationships, they can miss crucial exact matches. BM25 is a ranking function that uses lexical matching to find precise word or phrase matches. It's particularly effective for queries that include unique identifiers or technical terms." — Contextual Retrieval, Anthropic (https://www.anthropic.com/research/contextual-retrieval)

关键知识：

  • 嵌入与 BM25 在相反的方向上失败：语义搜索会漏掉精确术语（标识符、代码、罕见名称）；词法搜索会漏掉转述与含义。把两者与排名融合（rank fusion）结合能覆盖两种失败模式。
  • 查询模式决定配比：精确匹配查找（错误代码、SKU、条款编号）偏词法；自然语言问题偏语义；大多数生产系统需要混合式。
  • 数据形态决定单元：散文文档 → 上下文化文本块；代码库 → 带文件上下文的符号/函数级块；频繁更新的数据 → 索引新鲜度与重建索引路径与排名同样重要。
  • 检索并不总是答案：当语料放得下时，直接的长上下文纳入（带缓存）胜过检索；对结构化、可导航的数据，在文件系统上做智能体搜索能胜过向量索引。

关键技能：

  • 在修复之前先诊断检索失败：正确的块是从未被索引、被索引了但没排进 top-K，还是被检索了却被忽略？每种都有不同的修法。
  • 一步把策略与所描述的工作负载匹配：陈述数据形态 + 查询模式 → 所选策略（词法 / 语义 / 混合 / 不用 RAG）及理由。
  • 对照一个检索指标来调 top-K 与重排序，而不是凭感觉 —— 块更多不是免费的：它消耗 token，还可能把答案埋掉。

3.7 Evaluate connection protocols and select the appropriate integration mechanism (MCP, API/CLI, agent-to-agent)

Official wording: "Claude’s Model Context Protocol (MCP) connector feature allows you to connect to remote MCP servers directly from the Messages API without a separate MCP client." — MCP connector, Anthropic (https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)

Key knowledge:

  • MCP is the standard protocol for connecting agents to external systems and tools; the Messages API's MCP connector lets Claude call remote MCP servers directly, without a separate MCP client, over publicly exposed HTTP (Streamable HTTP and SSE transports; local stdio servers cannot be connected directly through the connector).
  • The connector configuration is two-part: an mcp_servers array (URL and authentication, OAuth Bearer supported) and an MCP toolset in tools (which tools are enabled and how each is configured); multiple servers can be connected in one request.
  • Direct API/CLI integration fits a single, fixed integration you fully control; MCP fits reusable, discoverable tool access shared across clients and teams; agent-to-agent fits delegating a sub-problem to another autonomous system rather than calling a deterministic function.
  • Code execution with MCP is the efficiency variant: present MCP servers as code APIs on a filesystem so the agent loads only the tool definitions it needs and filters data in the execution environment before it reaches the model (Anthropic's example cut tool-definition tokens from 150,000 to 2,000).

Key skills:

  • Choose by reuse and ownership: one-off internal endpoint → API; capability that several agents/clients should share → MCP server; open-ended work owned by another team/system → agent-to-agent.
  • Recognize the connector's hard constraints in a design review: remote server must be publicly reachable over HTTPS, and only tool calls are supported through the connector.
  • When tool count or result size is the bottleneck, propose the code-execution pattern instead of adding more direct tool calls.

3.8 Evaluate progressive discovery vs. monolithic context strategy

Official wording: "Context … must be treated as a finite resource with diminishing marginal returns. … good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." — Effective context engineering for AI agents, Anthropic (https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

Key knowledge:

  • Context is a finite resource with an "attention budget": good context engineering means finding the smallest set of high-signal tokens that maximizes the chance of the desired outcome — loading everything up front (monolithic) spends that budget on mostly irrelevant material.
  • Progressive disclosure loads information in layers as it becomes relevant: e.g., tool definitions presented as files on a filesystem that the agent explores on demand, or a search_tools tool with a detail-level parameter (name only → description → full schema).
  • Skills use the same three-level pattern: metadata always loaded, the SKILL.md body loaded when relevant, and linked reference files loaded only as needed.
  • Monolithic loading is not always wrong: a small, stable, always-relevant corpus (or tool set) is simpler and more predictable fully loaded — especially when prompt caching makes the repeated prefix cheap.

Key skills:

  • Estimate the load: count the tool definitions / documents; if they dwarf the task itself, choose progressive discovery and say what the discovery mechanism is (filesystem, search tool, skill levels).
  • Keep the always-loaded layer minimal but sufficient for routing: names and one-line descriptions must let the model decide what to fetch next.
  • Defend the monolithic choice when it is right: few tools, every request needs all of them, and caching neutralizes the cost.

Official sources: Effective context engineering for AI agents · Code execution with MCP (progressive disclosure)

4.1 Define evaluation metrics (accuracy, latency, cost, safety, security)

Official wording: "Building a successful LLM-based application starts with clearly defining your success criteria and then designing evaluations to measure performance against them. Most use cases need multidimensional evaluation along several success criteria." — Define success criteria and build evaluations, Anthropic (https://platform.claude.com/docs/en/test-and-evaluate/eval-tool)

Key knowledge:

  • Good success criteria are specific, measurable, achievable, and relevant — "good performance" is not a criterion; a quantified target is (the docs' own example: a hazy topic like safety becomes "less than 0.1% of outputs out of 10,000 trials flagged for toxicity").
  • Most use cases need multidimensional evaluation: accuracy alone hides latency, cost per task, and safety regressions. Evals also yield operational baselines for free — latency, token usage, cost per task, and error rates tracked on a static bank of tasks.
  • Separate capability metrics from regression metrics: capability evals ask what the agent can do (start with a low pass rate); regression evals ask whether it still does what it used to (should stay near 100%).
  • A metric needs a grader: code-based grading is fastest, most reliable, and most scalable; human grading is most flexible but slow and expensive; LLM-based grading is fast and flexible but must be validated for reliability before scaling.

Key skills:

  • Turn a vague requirement ("accurate and safe") into a metric set with thresholds: task success rate, p95 latency, cost per resolved task, and a safety flag rate — each with its grader type.
  • Pick the cheapest reliable grader per metric: exact/string match or state checks where the answer is verifiable; rubric-based LLM grading, calibrated against humans, where judgment is required.
  • Report metrics per domain/scenario, not one blended score, so a safety or cost regression cannot hide behind an accuracy gain.

  • 按领域/场景报告指标，而不是一个混合的总分，这样安全或成本回归就不能藏在准确性提升背后。

4.2 Design evaluation datasets and test frameworks using mixed methodologies

Official wording: "A task (a.k.a problem or test case) is a single test with defined inputs and success criteria. Each attempt at a task is a trial. A grader is logic that scores some aspect of the agent’s performance." — Demystifying evals for AI agents, Anthropic (https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Key knowledge:

  • The vocabulary is precise: a task is a single test with defined inputs and success criteria; each attempt is a trial (run several, because outputs vary); a grader scores an aspect of performance and can hold multiple assertions; a suite is a collection of tasks sharing a goal; the evaluation harness runs tasks, records transcripts, grades, and aggregates.
  • Design principles from the docs: be task-specific (mirror the real-world task distribution, including edge cases), automate grading when possible, and prioritize volume over quality — more tasks with slightly lower-signal automated grading beat a few hand-graded ones.
  • Mixed methodology means combining grader types in one framework: code-based graders for verifiable outcomes, model-based graders with rubrics for quality dimensions, and human grading for calibration — and grading the outcome (final environment state), not only the transcript, since an agent can claim success it did not achieve.
  • The Console Eval tool is the lightweight official harness: build test cases, run prompt versions against them, and compare results side by side.

Key skills:

  • Build a dataset from real material: production failures, support tickets, and edge cases first; synthetic cases to fill coverage gaps — never a dataset of only easy, happy-path tasks.
  • Structure every task with inputs, success criteria, and at least one grader before running anything; add multiple trials for tasks with variable outputs.
  • Keep capability and regression suites separate so hill-climbing on new skills cannot silently break old ones.

Official wording: "Combined with production monitoring, A/B tests, user research, and more, evals provide signals to continue improving Claude Code as it scales." — Demystifying evals for AI agents, Anthropic (https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Key knowledge:

  • Iteration without evals degenerates into reactive loops: fix one production failure, create another, with no way to distinguish a real regression from noise. Evals are what make an A/B comparison a measurement instead of an opinion.
  • The comparison unit is a version pair — prompt, model, or harness change — run against the same task bank, with the same graders; the Console Eval tool supports exactly this side-by-side prompt-version comparison.
  • Production signals complement offline evals: Anthropic describes Claude Code's improvement loop as evals combined with production monitoring, A/B tests, and user research — offline suites gate the change, online tests confirm it on real traffic.
  • Graduated tasks change role over time: a capability eval whose pass rate climbs high becomes part of the regression suite, so today's improvement becomes tomorrow's floor.

Key skills:

  • Change one variable per iteration (prompt OR model OR tool set), re-run the full suite, and compare per-domain scores — not just the headline number.
  • Set the promotion rule in advance: e.g., ship only if capability improves without any regression-suite drop or cost/latency breach.
  • Feed every production failure found after a change back into the dataset as a new task before the next iteration.

4.3 进行 A/B 测试与迭代改进

EN: Conduct A/B testing and iterative improvements

官方原文： "Combined with production monitoring, A/B tests, user research, and more, evals provide signals to continue improving Claude Code as it scales." — Demystifying evals for AI agents, Anthropic (https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

关键知识：

  • 没有评估的迭代会退化为反应式循环：修一个生产失败、造出另一个，且无法区分真正的回归与噪声。评估是让 A/B 比较成为度量而不是意见的东西。
  • 比较单元是一个版本对 —— 提示、模型或运行器的改动 —— 在同一个任务库、同一批评分器上运行；Console 的 Eval 工具恰好支持这种并排的提示版本比较。
  • 生产信号与离线评估互补：Anthropic 把 Claude Code 的改进回路描述为评估与生产监控、A/B 测试及用户研究相结合 —— 离线套件为改动把关，在线测试在真实流量上确认它。
  • 已毕业的任务会随时间改变角色：一个通过率爬升到很高的能力评估会成为回归套件的一部分，于是今天的改进变成明天的底线。

关键技能：

  • 每次迭代只改一个变量（提示 或 模型 或 工具集），重新运行完整套件，并比较各领域的分数 —— 而不只是头条数字。
  • 提前定好晋级规则：例如，只有当能力提升且回归套件无任何下降、成本/延迟不超标时才发布。
  • 在下一次迭代之前，把改动之后发现的每个生产失败作为新任务反馈进数据集。

4.4 Diagnose system issues (prompt failure, hallucinations, model mismatch)

Official wording: "Groundedness checks verify that claims are supported by retrieved sources, coverage checks define key facts a good answer must include, and source quality checks confirm the consulted sources are authoritative, rather than simply the first retrieved." — Demystifying evals for AI agents, Anthropic (https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Key knowledge:

  • Diagnose at the correct layer: the same symptom (a wrong answer) can come from retrieval returning irrelevant or stale chunks, from the prompt, from the tool layer, or from the model — each layer has a different fix, and changing the model is the last resort, not the first.
  • The transcript is the diagnostic instrument: it shows tool calls, intermediate results, and reasoning, letting you locate where the trajectory diverged; the outcome check tells you whether the failure is real or only cosmetic.
  • A classic pattern from the official guide's own sample items: confident-but-incorrect answers appearing right after a document refresh, with model and latency unchanged, point first at the retrieval/indexing step, not at the model.
  • Model mismatch is a real but specific diagnosis: the task's demands (reasoning depth, context length, speed) exceed or undershoot the chosen tier — detectable when a stronger model passes the same eval tasks the current one fails, with prompt and retrieval held constant.
  • Frontier models can also "fail" an eval by finding a legitimate loophole the task author missed — read failing transcripts before concluding the system is at fault; sometimes the eval is wrong.

Key skills:

  • Run the isolation sequence: check the retrieved context → check the tool calls and results in the transcript → check the prompt → only then test a different model on the same tasks.
  • Classify each production failure into a bucket (retrieval / prompt / tool / model / eval defect) and count the buckets; fix the biggest bucket first.
  • For hallucinations specifically, verify groundedness: are the claims supported by the retrieved sources, and was the right source retrieved at all?

4.4 诊断系统问题（提示失败、幻觉、模型不匹配）

关键知识：

  • 在正确的层上诊断：同一个症状（一个错误答案）可能来自检索返回了无关或过时的块、来自提示、来自工具层，或来自模型 —— 每层都有不同的修法，换模型是最后手段，不是第一选择。
  • 记录稿是诊断仪器：它显示工具调用、中间结果与推理，让你定位轨迹在哪里偏离；结果核查告诉你这个失败是真实的还是只是表面上的。
  • 一个来自官方指南自身样题的经典模式：在文档刷新之后突然出现自信但错误的答案，而模型与延迟未变，这首先指向检索/索引步骤，而不是模型。
  • 模型不匹配是一个真实但具体的诊断：任务的要求（推理深度、上下文长度、速度）超出或低于所选层级 —— 当更强的模型在提示与检索保持不变的情况下、通过了当前模型失败的同一批评估任务时，就能检测出来。
  • 前沿模型也可能通过找到任务作者漏掉的合理漏洞来「失败」一个评估 —— 在断定系统有错之前先读失败的记录稿；有时是评估错了。

关键技能：

  • 运行隔离序列：检查检索到的上下文 → 检查记录稿中的工具调用与结果 → 检查提示 → 最后才在同一批任务上测试不同的模型。
  • 把每个生产失败归入一个桶（检索 / 提示 / 工具 / 模型 / 评估缺陷），数一数各桶；先修最大的桶。
  • 专门针对幻觉，验证扎根性（groundedness）：这些主张是否被检索到的来源支持，以及正确的来源是否被检索到了。

4.5 Optimize token usage, latency, and cost-performance trade-offs

Official wording: "Free wins cut spend without touching quality: prompt caching, token hygiene, … and batch processing at 50% off for work that can wait up to 24 hours. Tradeoffs exchange cost for intelligence: model choice, effort, output caps and session budgets, an elapsed-time clock, and multimodel architectures." — Optimizing for cost and intelligence, Anthropic (https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)

Key knowledge:

  • Start with the free wins: prompt caching, token hygiene, a prompt audit against the model you are running, and batch processing at 50% off for work that can wait up to 24 hours — these cut spend without touching quality; only then trade along the frontier with model choice, effort, and output caps.
  • Prompt caching is a prefix mechanism: cache reads cost a fraction of base input price (10% standard), writes cost 25% more than base for the 5-minute TTL; the prefix is ordered tools → system → messages, and any change inside the prefix invalidates everything after it — so static content goes first, volatile content last.
  • Token waste in agents compounds: a long-running task resends its growing history every turn, so task cost grows roughly with the square of the turn count unless caching and context discipline intervene.
  • Context editing / trimming is a token-hygiene lever with limits: the cost-and-intelligence docs note it can cost more than it saves on short runs — measure it like everything else.

Key skills:

  • Profile before optimizing: use the per-response usage fields (uncached vs. cache-read vs. output tokens) to find whether spend is input repetition, oversized tool results, or verbose output — each has a different fix.
  • Apply the matching lever: repeated static prefix → caching; delay-tolerant volume → Message Batches; oversized tool results → filter/transform before they reach the model; wrong-sized model → re-tier and re-run evals to prove quality held.
  • Close the loop with the eval suite: an optimization is only accepted if the accuracy and safety metrics from 4.1 stay within their thresholds.

4.5 优化 token 用量、延迟与成本-性能权衡

关键知识：

  • 从免费的胜利开始：提示缓存（prompt caching）、token 卫生、针对你正在运行的模型做一次提示审计，以及对可以等待最长 24 小时的工作打五折的批处理 —— 这些能在不触碰质量的情况下削减支出；然后才用模型选择、effort 与输出上限沿前沿做权衡。
  • 提示缓存是一种前缀机制：缓存读取的成本是基础输入价格的一小部分（标准为 10%），写入比 5 分钟 TTL 的基础价格贵 25%；前缀的顺序是 tools → system → messages，前缀内的任何变化都会使它之后的一切失效 —— 因此静态内容放最前，易变内容放最后。
  • 智能体中的 token 浪费会累积：一个长时运行的任务每轮都重发它不断增长的历史，因此任务成本大致随轮次的平方增长，除非缓存与上下文纪律介入。
  • 上下文编辑 / 裁剪是一个有局限的 token 卫生杠杆：成本与智能文档指出，它在短运行上可能得不偿失 —— 像其他一切一样度量它。

关键技能：

  • 先剖析再优化：用每响应的 usage 字段（未缓存 vs. 缓存读取 vs. 输出 token）找出支出是输入重复、过大的工具结果，还是冗长的输出 —— 每种都有不同的修法。
  • 应用匹配的杠杆：重复的静态前缀 → 缓存；容忍延迟的批量工作 → Message Batches；过大的工具结果 → 在到达模型之前过滤/转换；尺寸不对的模型 → 重新分层并重跑评估以证明质量保持住了。
  • 用评估套件闭环：只有当 4.1 的准确性与安全指标保持在阈值之内时，一项优化才被接受。

5.1 Implement guardrails and safety controls

Official wording: "Apply the principle of least privilege so that a successful injection can do minimal damage: don’t give Claude access to secrets it doesn’t need, run tools in sandboxed environments, and scope permissions as narrowly as possible." — Mitigate jailbreaks and prompt injections, Anthropic (https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)

Key knowledge:

  • Guardrails are layered, not a single prompt instruction. Anthropic's jailbreak guidance separates two threat models: jailbreaks and direct prompt injection, where the user is the adversary, and indirect prompt injection, where trusted users are exposed through third-party content such as webpages, emails, documents, or tool results.
  • Input-side controls include harmlessness screens (a lightweight model such as Claude Haiku pre-screening input, with structured outputs constraining the verdict to a simple classification), input validation against known injection patterns, and system prompts that state ethical and legal boundaries and how to refuse.
  • For untrusted content: deliver third-party content only in tool_result blocks, never in system prompts; label its nature and source; state in the system prompt that tool/document content is untrusted data and must never override instructions; JSON-encode untrusted strings where possible.
  • Least privilege bounds the blast radius of a successful injection: do not give Claude secrets it does not need, run tools in sandboxed environments, and scope permissions as narrowly as possible. Screen tool outputs with the same classifier pattern before Claude acts on them.
  • Controls are proportional and maintained: throttle or ban repeat offenders, red-team your own agent with deliberately injected documents and tool outputs before deployment, and continuously monitor outputs to refine prompts, validation, and filtering.

Key skills:

  • Design a defense-in-depth stack (screen → validation → system-prompt policy → least-privilege tools → output monitoring) matched to whether the adversary is the user or the content.
  • Decide which actions need deterministic enforcement outside the prompt (permission rules, tool removal, sandboxing) versus prompt-level guidance.
  • Build a pre-deployment red-team test set of injection attempts and verify each layer catches what the previous layer misses.

5.1 实施护栏与安全控制

  • 设计一个纵深防御栈（筛查 → 校验 → 系统提示政策 → 最小权限工具 → 输出监控），与攻击者是用户还是内容相匹配。
  • 判断哪些行动需要在提示之外做确定性强制（权限规则、工具移除、沙箱），哪些用提示层面的指导即可。
  • 构建一个部署前的红队测试集，包含注入尝试，并验证每一层都能捕捉上一层漏掉的东西。

5.2 Identify risks, limitations, and failure modes of LLM systems

Official wording: "Even the most advanced language models, such as Claude, can sometimes generate text that is factually incorrect or inconsistent with the given context. This phenomenon, known as “hallucination,” can undermine the reliability of your AI-driven solutions." — Reduce hallucinations, Anthropic (https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)

Key knowledge:

  • Hallucination is a named, expected failure mode: even advanced models can generate text that is factually incorrect or inconsistent with the given context. Anthropic's mitigations are partial by design — allowing Claude to say "I don't know," grounding in direct quotes, and verifying claims with citations reduce, but do not eliminate, the risk.
  • Capability risk is governed at Anthropic through the Responsible Scaling Policy (RSP) and its AI Safety Levels (ASL): models are evaluated before release in catastrophic-risk areas such as CBRN, cybersecurity, and autonomous capabilities, and the required safeguards scale with the assessed level.
  • System cards are the public record of that evaluation: pre-deployment safety tests, Usage Policy violation tests, agentic safety evaluations (computer use, coding), alignment assessments, and the ASL standard under which a model was deployed.
  • Agentic failure modes extend beyond wrong text: a compromised or misled agent can take real actions, so risk analysis must cover tool misuse, indirect injection through retrieved content, and error propagation across steps — not only output quality.
  • Known limitations to design around include finite context and degraded recall over long inputs, sensitivity to ambiguous instructions, and the gap between a model's confident tone and its actual reliability.

Key skills:

  • Write a failure-mode inventory for a given system (hallucination, injection, tool misuse, over-permissioned actions, stale or wrong retrieval) and map each mode to a detection method and a mitigation.
  • Read a system card and extract what was actually tested, under which ASL standard the model shipped, and what that implies for your own deployment risk.
  • Distinguish risks the model provider has evaluated from risks that remain the deploying architect's responsibility.

Official sources: Reduce hallucinations · Responsible Scaling Policy · Claude 4 System Card

5.2 识别 LLM 系统的风险、局限与失败模式

EN: Identify risks, limitations, and failure modes of LLM systems

官方原文： "Even the most advanced language models, such as Claude, can sometimes generate text that is factually incorrect or inconsistent with the given context. 关键知识：

  • 幻觉（Hallucination）是一个被点名的、预期中的失败模式：即使是先进模型也可能生成事实上不正确、或与给定上下文不一致的文本。Anthropic 的缓解措施按设计就是部分的 —— 允许 Claude 说「我不知道」、扎根于直接引文、用引注核查主张，这些能减少但不能消除风险。
  • 能力风险在 Anthropic 内部由负责任扩展政策（Responsible Scaling Policy，RSP）及其 AI 安全等级（AI Safety Levels，ASL）治理：模型在发布前会在 CBRN、网络安全与自主能力等灾难性风险领域接受评估，所需保障措施随评估等级而扩展。
  • 系统卡（System cards）是该评估的公开记录：部署前安全测试、使用政策（Usage Policy）违规测试、智能体安全评估（计算机使用、编程）、对齐评估，以及模型部署所依据的 ASL 标准。
  • 智能体失败模式超出错误文本的范围：一个被攻陷或被误导的智能体能采取真实行动，因此风险分析必须覆盖工具滥用、通过检索内容进行的间接注入，以及跨步骤的错误传播 —— 而不只是输出质量。
  • 需要围绕其设计的已知局限包括：有限的上下文与长输入下退化的回忆、对含糊指令的敏感，以及模型的自信语气与其实际可靠性之间的差距。

关键技能：

  • 为一个给定系统写一份失败模式清单（幻觉、注入、工具滥用、权限过大的行动、过时或错误的检索），并把每种模式映射到一种检测方法与一种缓解措施。
  • 阅读一份系统卡，提取出实际测试了什么、模型依据哪个 ASL 标准发布，以及这对你自己的部署风险意味着什么。
  • 区分模型提供商已经评估过的风险，与仍然属于部署架构师责任的风险。

5.3 Apply human-in-the-loop validation strategies

Official wording: "MCP toolsets default to always_ask. This ensures that new tools added to an MCP server do not run in your application without approval." — Permission policies, Anthropic (https://platform.claude.com/docs/en/managed-agents/permission-policies)

Key knowledge:

  • Human-in-the-loop (HITL) is implemented as a permission decision, not a hope: in the Agent SDK / Claude Code permission flow, calls that no hook, deny/ask/allow rule, or permission mode has already resolved reach the canUseTool callback, which pauses execution until a human (or your application logic) returns allow or deny.
  • Permission policies for server-executed tools express the same idea declaratively: always_allow runs automatically, always_ask pauses for approval, and auto has the server evaluate each call and run it, deny it, or pause for approval. MCP toolsets default to always_ask, so newly added tools do not run unapproved.
  • Approval belongs on irreversible or high-impact actions (deleting files, issuing refunds, sending external messages), while low-risk read-only actions are normally pre-approved by allow rules to avoid approval fatigue.
  • A pending approval can outlive the process: the docs recommend deferring via a PreToolUse hook and resuming from the persisted session rather than blocking a callback indefinitely, and using a PermissionRequest hook to notify approvers externally (Slack, email, push).

Key skills:

  • Place approval gates by risk tier: auto-allow reads, ask for writes and external actions, deny outright what the role never needs — remembering that removing a tool beats guarding it.
  • Design the approval experience: show the approver the exact tool and input, record the decision, and handle timeouts and deferred resumption.
  • Recognize when HITL is the wrong control (high-volume, low-risk, latency-critical paths) and substitute sampling, post-hoc audit, or automated checks.

Official sources: Permission policies (Managed Agents) · Configure permissions — Claude Code · Mitigate jailbreaks and prompt injections

5.3 运用人在回路验证策略

EN: Apply human-in-the-loop validation strategies

官方原文： "MCP toolsets default to always_ask. This ensures that new tools added to an MCP server do not run in your application without approval." — Permission policies, Anthropic (https://platform.claude.com/docs/en/managed-agents/permission-policies)

关键知识：

  • 人在回路（Human-in-the-loop，HITL）是作为一个权限决定来实施的，而不是一种期望：在 Agent SDK / Claude Code 的权限流程中，那些没有被 hook、deny/ask/allow 规则或权限模式已经裁决的调用，会到达 canUseTool 回调，它暂停执行，直到人类（或你的应用逻辑）返回允许或拒绝。
  • 针对服务器执行工具的权限政策以声明式表达同一个思想：always_allow 自动运行，always_ask 暂停等待批准，auto 由服务器评估每次调用并运行它、拒绝它或暂停等待批准。MCP 工具集默认是 always_ask，因此新添加的工具不会未经批准就运行。
  • 批准属于不可逆或高影响的行动（删除文件、发放退款、发送外部消息），而低风险的只读行动通常由 allow 规则预先批准，以避免批准疲劳。
  • 一个待处理的批准可以比进程活得更久：文档建议通过 PreToolUse hook 延迟处理、并从持久化的会话恢复，而不是无限期阻塞一个回调；并使用 PermissionRequest hook 在外部通知批准人（Slack、邮件、推送）。

关键技能：

  • 按风险层级放置批准关卡：读取自动允许，写入与外部行动要询问，该角色从不需要的直接拒绝 —— 并记住，移除一个工具胜过守卫它。
  • 设计批准体验：向批准人展示确切的工具与输入，记录决定，并处理超时与延迟恢复。
  • 识别 HITL 是错误控制的场合（高吞吐、低风险、对延迟关键的路径），并代之以抽样、事后审计或自动化检查。

官方来源： 权限政策（托管智能体）(Permission policies (Managed Agents)) · 配置权限 — Claude Code（Configure permissions — Claude Code） · 缓解越狱与提示注入（Mitigate jailbreaks and prompt injections）

5.4 Ensure compliance with regulations (e.g., GDPR, HIPAA, FedRAMP)

Official wording: "Under a Legacy ZDR arrangement, Anthropic does not store customer prompts or responses at rest after the API response is returned." — API and data retention, Anthropic (https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)

Key knowledge:

  • Data handling is the concrete compliance surface. Anthropic offers two arrangements for the Claude API: zero data retention (ZDR), under which customer prompts and responses are not stored at rest after the response is returned, and HIPAA readiness for organizations handling protected health information, which requires a signed Business Associate Agreement (BAA).
  • Outside those arrangements: retained data is never used for model training without express permission, only what is technically necessary is retained, conversation content is not retained by default (with stated exceptions, e.g. certain models requiring 30-day retention), and retained data is purged on the shortest practical TTL.
  • Eligibility is per feature and per organization: ZDR is enabled per organization through the account team and does not automatically extend to other organizations; not every API feature is eligible under ZDR or HIPAA arrangements, and in a HIPAA-configured organization non-eligible features are excluded.
  • Consumer products and commercial terms are different worlds: compliance claims that hold for the API under Commercial Terms do not transfer to Free/Pro/Max consumer plans, and Claude delivered through cloud partners sits under those platforms' terms.
  • The architect's job is mapping: identify which regulation applies (GDPR for EU personal data, HIPAA for PHI, FedRAMP for US federal use), which data classes the system touches, and which arrangement, region, and feature set keeps that data inside the compliant boundary.

Key skills:

  • Audit a proposed architecture against a regulation: data classes, retention, training use, subprocessors/cloud route, and whether a BAA or ZDR arrangement must be in place before any regulated data flows.
  • Restrict a deployment to eligible features only, and design fallbacks (refuse, redact, route elsewhere) for requests that would leave the compliant boundary.
  • State compliance limits honestly to stakeholders: a vendor BAA or ZDR arrangement supports, but does not by itself make, the customer's application compliant.

Official sources: API and data retention · Mitigate jailbreaks and prompt injections

5.4 确保遵守法规（例如 GDPR、HIPAA、FedRAMP）

EN: Ensure compliance with regulations (e.g., GDPR, HIPAA, FedRAMP)

官方原文： "Under a Legacy ZDR arrangement, Anthropic does not store customer prompts or responses at rest after the API response is returned." — API and data retention, Anthropic (https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)

关键知识：

  • 数据处理是具体的合规表面。Anthropic 为 Claude API 提供两种安排：零数据保留（zero data retention，ZDR），在该安排下客户的提示与响应在响应返回后不落地存储；以及为处理受保护健康信息（PHI）的组织提供的 HIPAA 就绪安排，它要求签署一份业务伙伴协议（Business Associate Agreement，BAA）。

关键技能：

  • 对照一部法规审计一个拟议架构：数据类别、保留、训练使用、子处理者/云路线，以及在任何受监管数据流动之前是否必须先有 BAA 或 ZDR 安排。
  • 把部署限制在有资格的功能内，并为会离开合规边界的请求设计回退方案（拒绝、脱敏、路由到别处）。
  • 对利益相关方诚实陈述合规的限度：厂商的 BAA 或 ZDR 安排是支持，但其本身并不能使客户的应用合规。

5.5 Address ethical AI considerations (bias, fairness, transparency)

Official wording: "In order to be both safe and beneficial, we believe all current Claude models should be: … Broadly ethical: Having good personal values, being honest, and avoiding actions that are inappropriately dangerous or harmful." — Claude's Constitution, Anthropic (https://www.anthropic.com/constitution)

Key knowledge:

  • Anthropic publishes Claude's governing principles: Claude's Constitution (January 2026, released in full under CC0) is a detailed, public description of Anthropic's intentions for Claude's values and behavior — transparency about intended behavior is itself part of the governance model.
  • Constitutional AI is the training approach behind it: the model is trained to critique and revise its own responses against an explicit set of principles, rather than relying only on human preference labels.

Key skills:

  • Evaluate a use case for disparate impact: identify affected groups, define what a biased output would look like, and test for it before launch and after model or prompt changes.
  • Choose transparency mechanisms proportionate to the stakes: citations and source display for factual claims, clear AI disclosure, and human review for decisions about people.
  • Escalate or refuse use cases where the ethical risk cannot be mitigated — and document that decision for stakeholders.

6.3 Manage stakeholder feedback loops and expectation alignment (including SLAs)

Key skills:

  • Design a team's baseline configuration: managed policy for non-negotiables, project settings shared in version control, and personal overrides kept local.

7.3 Support debugging and operational issue resolution

Official wording: "When Claude ignores an instruction or a feature you configured doesn’t appear, the cause is usually that the file didn’t load, it loaded from a different location than you expected, or another file overrode it." — Debug your configuration, Anthropic (https://code.claude.com/docs/en/debug-your-config)

Key knowledge:

  • Claude Code ships a structured debugging path: /context shows what occupies the context window and where each item loaded from; /doctor checks installation health, invalid settings files, and unused extensions and proposes fixes; /debug [issue] enables debug logging; /status shows active settings sources including whether managed settings are in effect.
  • The debug guide's central lesson is that most "Claude ignored my instruction" cases are configuration resolution problems — the file did not load, loaded from a different location than expected, or was overridden by a closer scope or an environment variable — not model problems.
  • Component-specific checks exist for each surface: /mcp for server connection status (project-scoped servers need a one-time approval; a connected server listing zero tools has a tool-list problem), /hooks for registered hooks (a hook that does not appear was not loaded; one that appears but does not fire usually has a matcher problem), and /permissions for resolved rules.

Operational monitoring (OpenTelemetry metrics and events, analytics) covers the fleet-level view beyond a single session.

Key skills:

  • Triage in order: reproduce, inspect what loaded (/context, /status), check the specific surface (/mcp, /hooks, /permissions), then bisect with safe mode before changing anything.
  • Distinguish the three root-cause classes — not loaded, loaded from the wrong place, overridden — and fix at the scope that actually wins.
  • Feed recurring operational issues back into team configuration (a corrected matcher, a missing deny rule, a managed-settings fix) so the same incident does not recur per developer.

  • B. Remove the refund and delete tools from the agent's configuration entirely.
  • C. Keep all tools but add a confirmation prompt before refunds and deletions.
  • D. Replace the agent with a larger model that follows instructions more reliably.

Answer: B. Least privilege means removing capabilities the role does not require, eliminating the attack surface rather than monitoring or guarding it. Logging (A) and confirmations (C) are detective/compensating controls, not removal of unnecessary privilege; model size (D) is unrelated to authorization scope.

Sample 2 · Domain 2 — Models, Prompting & Context Engineering

An application sends the same 8,000-token system prompt and policy document on every request, followed by a short, varying user message. Latency and cost are both concerns. Which optimization most directly addresses both?

  • A. Truncate the policy document to the first 1,000 tokens.
  • B. Switch to the smallest available model regardless of task fit.
  • C. Place the static system prompt and policy before the dynamic content and enable prompt caching.
  • D. Move the policy document into a few-shot example block.

Answer: C. Ordering stable content first and enabling prompt caching lets repeated prefixes be reused, reducing both time-to-first-token and per-request cost without discarding required context. Truncation (A) loses needed policy; downsizing blindly (B) risks quality; relocating to few-shot (D) does not create a cacheable, reusable prefix.

Sample 3 · Domain 4 — Evaluation, Testing & Optimization

A RAG system suddenly returns confident but incorrect answers after a document refresh, while latency and model version are unchanged. What is the most likely first place to investigate?

  • A. The model weights have silently changed.
  • B. The retrieval/indexing step is returning irrelevant or stale chunks.
  • C. The temperature setting is too low.
  • D. The context window has shrunk.

Answer: B. Confident-but-wrong answers following a document refresh, with model and latency unchanged, point to retrieval feeding the model poor context — for example a broken re-index or mismatched embeddings. The other options would not be triggered specifically by a document refresh.

样题 1 · 领域 3 — 集成（Sample 1 · Domain 3 — Integration）

一个团队暴露了一个客户支持智能体，它能读工单、起草回复、发放退款并删除用户账户。支持人员实际只需要读工单和起草回复。运用最小权限原则，哪项改动最能降低风险？

  • A. 为退款与删除工具添加日志，以便滥用可在事后审计。
  • B. 把退款与删除工具从智能体的配置中完全移除。
  • C. 保留全部工具，但在退款与删除之前添加一个确认提示。
  • D. 把智能体换成一个更大的、更可靠地遵循指令的模型。

答案：B。 最小权限意味着移除该角色不需要的能力，消除攻击面，而不是监控或守卫它。日志（A）与确认（C）是侦测性/补偿性控制，不是移除不必要的权限；模型大小（D）与授权范围无关。

样题 2 · 领域 2 — 模型、提示与上下文工程（Sample 2 · Domain 2 — Models, Prompting & Context Engineering）

一个应用在每次请求中都发送同样的 8,000 token 系统提示与政策文档，后面跟着一条简短的、变化的用户消息。延迟与成本都令人担忧。哪项优化最直接地同时解决这两者？

  • A. 把政策文档截断到前 1,000 个 token。
  • B. 不顾任务适配，换成可用的最小模型。
  • C. 把静态的系统提示与政策放在动态内容之前，并启用提示缓存（prompt caching）。
  • D. 把政策文档移进一个少样本示例块。

答案：C。 把稳定内容排在前面并启用提示缓存，使重复的前缀能被复用，在不丢弃必需上下文的情况下同时减少首 token 时间与每请求成本。截断（A）会丢失需要的政策；盲目缩小模型（B）有质量风险；移到少样本（D）并不能创造一个可缓存、可复用的前缀。

样题 3 · 领域 4 — 评估、测试与优化（Sample 3 · Domain 4 — Evaluation, Testing & Optimization）

一个 RAG 系统在文档刷新之后突然返回自信但错误的答案，而延迟与模型版本未变。最可能首先要调查的地方是哪里？

  • A. 模型权重已经悄悄变了。
  • B. 检索/索引步骤正在返回无关或过时的块。
  • C. 温度（temperature）设置太低。
  • D. 上下文窗口已经缩小了。

答案：B。 在文档刷新之后出现自信但错误的答案，且模型与延迟未变，这指向检索在给模型喂差的上下文 —— 例如一次坏掉的重建索引或不匹配的嵌入。其他选项不会被一次文档刷新专门触发。
