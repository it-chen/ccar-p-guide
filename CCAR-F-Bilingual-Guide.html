Introduction

The Claude Certified Architect – Foundations certification validates that practitioners can make informed decisions about tradeoffs when implementing real-world solutions with Claude. This exam tests foundational knowledge across Claude Code, the Claude Agent SDK, the Claude API, and Model Context Protocol (MCP), the core technologies used to build production-grade applications with Claude.

Questions on this exam are grounded in realistic scenarios drawn from actual customer use cases, including building agentic systems for customer support, designing multi-agent research pipelines, integrating Claude Code into CI/CD workflows, building developer productivity tools, and extracting structured data from unstructured documents. Candidates must demonstrate not only conceptual knowledge but practical judgment about architecture, configuration, and tradeoffs in production deployments.

This guide is the study companion to the official Exam Guide, which is the authoritative reference for the credential: its content, domains and task statements, sample questions, and preparation strategies.

Target Candidate

The ideal candidate for this certification is a solution architect who designs and implements production applications with Claude. This candidate has hands-on experience with:

  • Building agentic applications using the Claude Agent SDK, including multi-agent orchestration, subagent delegation, tool integration, and lifecycle hooks
  • Configuring and customizing Claude Code for team workflows using CLAUDE.md files, Agent Skills, MCP server integrations, and plan mode
  • Designing Model Context Protocol (MCP) tool and resource interfaces for backend system integration
  • Engineering prompts that produce reliable structured output, leveraging JSON schemas, few-shot examples, and extraction patterns
  • Managing context windows effectively across long documents, multi-turn conversations, and multi-agent handoffs
  • Integrating Claude into CI/CD pipelines for automated code review, test generation, and pull request feedback
  • Making sound escalation and reliability decisions, including error handling, human-in-the-loop workflows, and self-evaluation patterns

The candidate typically has 6+ months of practical experience building with Claude APIs, Agent SDK, Claude Code, and MCP, understanding both the capabilities and limitations of large language models in production environments.

1.1 Design and implement agentic loops for autonomous task execution

Official wording: "Claude responds with stop_reason: "tool_use" and one or more tool_use blocks. Your code runs the operation and sends back a tool_result." — Tool use with Claude, Anthropic (https://platform.claude.com/docs/en/build-with-claude/tool-use)

Key knowledge:

  • The agentic loop lifecycle: sending requests to Claude, inspecting stop_reason ("tool_use" vs "end_turn"), executing requested tools, and returning results for the next iteration
  • How tool results are appended to conversation history so the model can reason about the next action
  • The distinction between model-driven decision-making (Claude reasons about which tool to call next based on context) and pre-configured decision trees or tool sequences

Key skills:

  • Implementing agentic loop control flow that continues when stop_reason is "tool_use" and terminates when stop_reason is "end_turn"
  • Adding tool results to conversation context between iterations so the model can incorporate new information into its reasoning
  • Avoiding anti-patterns such as parsing natural language signals to determine loop termination, setting arbitrary iteration caps as the primary stopping mechanism, or checking for assistant text content as a completion indicator

  • 避免反模式，例如解析自然语言信号来判断循环终止、把任意迭代上限作为主要停止机制，或检查助手文本内容作为完成指标

1.2 Orchestrate multi-agent systems with coordinator-subagent patterns

Official wording: "Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." — How we built our multi-agent research system, Anthropic (https://www.anthropic.com/research/multi-agent-research-system)

Key knowledge:

  • Hub-and-spoke architecture where a coordinator agent manages all inter-subagent communication, error handling, and information routing
  • How subagents operate with isolated context — they do not inherit the coordinator's conversation history automatically
  • The role of the coordinator in task decomposition, delegation, result aggregation, and deciding which subagents to invoke based on query complexity
  • Risks of overly narrow task decomposition by the coordinator, leading to incomplete coverage of broad research topics

Key skills:

  • Designing coordinator agents that analyze query requirements and dynamically select which subagents to invoke rather than always routing through the full pipeline
  • Partitioning research scope across subagents to minimize duplication (e.g., assigning distinct subtopics or source types to each agent)
  • Implementing iterative refinement loops where the coordinator evaluates synthesis output for gaps, re-delegates to search and analysis subagents with targeted queries, and re-invokes synthesis until coverage is sufficient
  • Routing all subagent communication through the coordinator for observability, consistent error handling, and controlled information flow

1.3 Configure subagent invocation, context passing, and spawning

Key knowledge:

  • The Task tool as the mechanism for spawning subagents, and the requirement that allowedTools must include "Task" for a coordinator to invoke subagents

  • Fork-based session management for exploring divergent approaches from a shared analysis baseline

  • Using structured data formats to separate content from metadata (source URLs, document names, page numbers) when passing context between agents to preserve attribution
  • Spawning parallel subagents by emitting multiple Task tool calls in a single coordinator response rather than across separate turns
  • Designing coordinator prompts that specify research goals and quality criteria rather than step-by-step procedural instructions, to enable subagent adaptability

1.4 Implement multi-step workflows with enforcement and handoff patterns

Official wording: "The Claude Agent SDK provides permission controls to manage how Claude uses tools. Use permission modes and rules to define what's allowed automatically, and the canUseTool callback to handle calls that still need approval." — Configure permissions, Anthropic (https://platform.claude.com/docs/en/agent-sdk/permissions)

Key knowledge:

  • The difference between programmatic enforcement (hooks, prerequisite gates) and prompt-based guidance for workflow ordering
  • When deterministic compliance is required (e.g., identity verification before financial operations), prompt instructions alone have a non-zero failure rate
  • Structured handoff protocols for mid-process escalation that include customer details, root cause analysis, and recommended actions

Key skills:

  • 用于崩溃恢复的结构化状态持久化：每个智能体把状态导出到已知位置，协调者在恢复时加载一份清单（manifest）

  • C. Add few-shot examples showing the agent always calling get_customer first, even when customers volunteer order details.
  • D. Implement a routing classifier that analyzes each request and enables only the subset of tools appropriate for that request type.

Answer: A. When a specific tool sequence is required for critical business logic (like verifying customer identity before processing refunds), programmatic enforcement provides deterministic guarantees that prompt-based approaches cannot. Options B and C rely on probabilistic LLM compliance, which is insufficient when errors have financial consequences. Option D addresses tool availability rather than tool ordering, which is not the actual problem.

Question 2

Production logs show the agent frequently calls get_customer when users ask about orders (e.g., "check my order #12345"), instead of calling lookup_order. Both tools have minimal descriptions ("Retrieves customer information" / "Retrieves order details") and accept similar identifier formats. What's the most effective first step to improve tool selection reliability?

  • A. Add few-shot examples to the system prompt demonstrating correct tool selection patterns, with 5-8 examples showing order-related queries routing to lookup_order.

  • C. Implement a routing layer that parses user input before each turn and pre-selects the appropriate tool based on detected keywords and identifier patterns.
  • D. Consolidate both tools into a single lookup_entity tool that accepts any identifier and internally determines which backend to query.

Answer: B. Tool descriptions are the primary mechanism LLMs use for tool selection. When descriptions are minimal, models lack the context to differentiate between similar tools. Option B directly addresses this root cause with a low-effort, high-leverage fix. Few-shot examples (A) add token overhead without fixing the underlying issue. Consolidating tools (D) is a valid architectural choice but requires more effort than a "first step" warrants when the immediate problem is inadequate descriptions.

  • A. 项目仓库中的 .claude/commands/ 目录
  • B. 每个开发者主目录中的 ~/.claude/commands/
  • C. 项目根目录的 CLAUDE.md 文件
  • D. 带 commands 数组的 .claude/config.json 文件

答案：A。 项目级（project-scoped）自定义斜杠命令应存放在仓库内的 .claude/commands/ 目录。这些命令受版本控制，开发者克隆或拉取仓库时自动可用。选项 B（~/.claude/commands/）用于不通过版本控制共享的个人命令。选项 C（CLAUDE.md）用于项目指令与上下文，而不是命令定义。选项 D 描述的配置机制在 Claude Code 中并不存在。

问题 5

你被指派把团队的单体应用重构为微服务。这将涉及跨数十个文件的改动，并需要就服务边界与模块依赖做出决策。你应该采取哪种方式？

  • A. 进入计划模式（plan mode），探索代码库、理解依赖，并在动手改动前设计实现方案。
  • B. 从直接执行开始，逐步改动，让实现过程揭示自然的服务边界。
  • C. 使用直接执行，并给出全面细致的前置指令，精确说明每个服务应如何组织。
  • D. 先以直接执行模式开始，只有在实现中遇到意外复杂性时才切换到计划模式。

答案：A。 计划模式正是为涉及大规模改动、多种可行方案与架构决策的复杂任务设计的 —— 这正是单体到微服务重构所需要的。它能在承诺改动之前安全地探索代码库并做设计。选项 B 的风险是依赖关系发现得太晚、导致昂贵的返工。选项 C 假设你在不探索代码的情况下就已经知道正确的结构。选项 D 忽略了一个事实：复杂性已经写在需求里了，而不是可能在途中才出现的东西。

问题 6

你的代码库有不同区域、不同的编码约定：React 组件用带 hooks 的函数式风格，API 处理器用带特定错误处理的 async/await，数据库模型遵循仓储（repository）模式。测试文件散布在整个代码库中、紧挨着被测代码（例如 Button.test.tsx 紧挨着 Button.tsx），你希望所有测试无论位置如何都遵循同一套约定。确保 Claude 在生成代码时自动应用正确约定的最易维护方式是什么？

  • A. 在 .claude/rules/ 中创建规则文件，用 YAML frontmatter 指定 glob 模式，根据文件路径有条件地应用约定
  • B. 把所有约定汇总到根 CLAUDE.md 文件中，按区域分节，依赖 Claude 推断哪一节适用
  • C. 在 .claude/skills/ 中为每种代码类型创建技能，把相关约定写进各自的 SKILL.md 文件
  • D. 在每个子目录中放置一个单独的 CLAUDE.md 文件，包含该区域的专属约定

答案：A。 选项 A 正确，因为带 glob 模式（如 **/*.test.tsx）的 .claude/rules/ 能根据文件路径自动应用约定，不受目录位置限制，这对散布在整个代码库中的测试文件至关重要。选项 B 依赖推断而非显式匹配，不可靠。选项 C 需要手动调用技能，或依赖 Claude 自行选择加载，与基于文件路径确定性「自动」应用的要求相矛盾。选项 D 难以处理散布在许多目录中的文件，因为 CLAUDE.md 文件是与目录绑定的。

问题 7

在主题「AI 对创意产业的影响」上运行系统后，你观察到每个子智能体都成功完成了任务：网络搜索智能体找到了相关文章，文档分析智能体正确总结了论文，综合智能体产出了连贯的输出。然而，最终报告只覆盖了视觉艺术，完全遗漏了音乐、写作和电影制作。查看协调者的日志，你发现它把主题分解成了三个子任务：「AI 在数字艺术创作中的应用」「AI 在平面设计中的应用」「AI 在摄影中的应用」。最可能的根源是什么？

  • A. 综合智能体缺乏识别其收到的研究结果中覆盖缺口的指令。
  • B. 协调者智能体的任务分解太窄，导致子智能体的分工没有覆盖该主题的所有相关领域。
  • C. 网络搜索智能体的查询不够全面，需要扩展到更多创意产业部门。
  • D. 文档分析智能体因相关性标准过严，过滤掉了与非视觉创意产业相关的来源。

答案：B。 协调者的日志直接揭示了根源：它把「创意产业」只分解成了视觉艺术子任务（数字艺术、平面设计、摄影），完全遗漏了音乐、写作和电影。子智能体都正确执行了被分配的任务 —— 问题出在它们被分配了什么。选项 A、C、D 都错误地指责了在各自分配范围内正常工作的下游智能体。

问题 8

网络搜索子智能体在研究一个复杂主题时超时了。你需要设计这个失败信息如何回流给协调者智能体。哪种错误传播方式最能支持智能恢复？

  • A. 向协调者返回结构化错误上下文，包括失败类型、尝试过的查询、任何部分结果，以及潜在的替代方案。
  • B. 在子智能体内部实现带指数退避的自动重试逻辑，只有在所有重试都耗尽后才返回一个笼统的「搜索不可用」状态。
  • C. 在子智能体内部捕获超时，返回一个标记为成功的空结果集。
  • D. 把超时异常直接传播到顶层处理器，终止整个研究工作流。

答案：A。 结构化错误上下文让协调者拥有做出智能恢复决策所需的信息 —— 是用修改过的查询重试、尝试替代方案，还是带着部分结果继续。选项 B 的笼统状态向协调者隐藏了宝贵的上下文，使其无法做出知情决策。选项 C 把失败标记为成功、压制了错误，阻止了任何恢复，并可能产生不完整的研究输出。选项 D 在恢复策略本可能成功时，不必要地终止了整个工作流。

问题 9

在测试中，你观察到综合智能体在合并研究结果时经常需要核实具体的论断。目前，每当需要核实时，综合智能体把控制权交还协调者，协调者调用网络搜索智能体，然后带着结果重新调用综合。这给每个任务增加了 2-3 次往返，延迟增加 40%。你的评估显示，这些核实中有 85% 是简单的事实核查（日期、姓名、统计数据），15% 需要更深入的调查。在保持系统可靠性的同时减少开销的最有效方法是什么？

  • A. 给综合智能体一个受限的 verify_fact 工具做简单查询，复杂核实继续通过协调者委派给网络搜索智能体。
  • B. 让综合智能体把所有核实需求累积起来，在其一遍处理结束时批量返回给协调者，由协调者一次性全部发给网络搜索智能体。
  • C. 给综合智能体全部网络搜索工具的访问权，使它能直接处理任何核实需求，无需经协调者往返。
  • D. 让网络搜索智能体在初步研究时主动缓存每个来源周围的额外上下文，预判综合智能体可能需要核实什么。

答案：A。 选项 A 应用了最小权限原则（principle of least privilege）：只给综合智能体处理 85% 常见情况（简单事实核查）所需的东西，复杂情况则保留现有的协调模式。选项 B 的批处理方式会造成阻塞依赖，因为综合步骤可能依赖先前已核实的事实。选项 C 给综合智能体过度授权，违反关注点分离。选项 D 依赖投机性缓存，无法可靠预判综合智能体需要核实什么。

问题 10

你的流水线脚本运行 claude "Analyze this pull request for security issues"，但作业无限期挂起。日志表明 Claude Code 正在等待交互输入。在自动化流水线中运行 Claude Code 的正确方式是什么？

  • A. 添加 -p 标志：claude -p "Analyze this pull request for security issues"
  • B. 在运行命令前设置环境变量 CLAUDE_HEADLESS=true
  • C. 把 stdin 从 /dev/null 重定向：claude "Analyze this pull request for security issues" < /dev/null
  • D. 添加 --batch 标志：claude --batch "Analyze this pull request for security issues"

答案：A。 -p（或 --print）标志是以非交互模式运行 Claude Code 的官方文档方式。它处理提示、把结果输出到 stdout，然后退出，不等待用户输入 —— 正是 CI/CD 流水线所需要的。其他选项引用了不存在的功能（CLAUDE_HEADLESS 环境变量、--batch 标志），或使用不能正确处理 Claude Code 命令语法的 Unix 变通办法。

问题 11

你的团队想降低自动化分析的 API 成本。目前，实时 Claude 调用支撑着两个工作流：（1）一个阻塞性的合并前检查，开发者必须等它完成才能合并；（2）一个连夜生成、供次日早上评审的技术债报告。你的经理提议把两者都切换到消息批处理 API（Message Batches API），以获得其 50% 的成本节省。你应如何评估这个提议？

  • A. 只对技术债报告使用批处理；合并前检查保持实时调用。
  • B. 两个工作流都切换到批处理，用状态轮询检查是否完成。
  • C. 两个工作流都保持实时调用，以避免批处理结果排序问题。
  • D. 两者都切换到批处理，若批处理耗时过长则以超时回退到实时调用。

答案：A。 消息批处理 API 提供 50% 的成本节省，但处理时间最长可达 24 小时，且不保证延迟 SLA。这使它不适合开发者要等待结果的阻塞性合并前检查，但非常适合技术债报告这样的连夜批处理作业。选项 B 错误，因为对阻塞性工作流来说，依赖「通常更快」的完成时间不可接受。选项 C 反映了一个误解 —— 批处理结果可以用 custom_id 字段关联。选项 D 增加了不必要的复杂性，而更简单的解法是让每个 API 各自匹配适合的用例。

问题 12

一个拉取请求修改了库存跟踪模块的 14 个文件。你的单遍审查（把所有文件放在一起分析）产生不一致的结果：某些文件有详细反馈，另一些只有肤浅评论；明显的 bug 被遗漏；反馈还自相矛盾 —— 在一个文件中把某种模式标记为问题，却在同一个 PR 的其他地方批准了相同的代码。你应如何重构这个审查？

  • A. 拆分为聚焦的多遍：先逐个文件单独分析局部问题，再运行一个单独的、聚焦集成的遍，检查跨文件数据流。
  • B. 要求开发者在自动化审查运行前，把大型 PR 拆成 3-4 个文件的较小提交。
  • C. 切换到上下文窗口更大的更高层级模型，让 14 个文件在单遍中都得到足够关注。
  • D. 对整个 PR 运行三遍独立审查，只标记在至少两遍中都出现的问题。

答案：A。 把审查拆成聚焦的多遍直接解决根源：一次处理许多文件时的注意力稀释（attention dilution）。逐文件分析保证深度一致，单独的集成遍则捕获跨文件问题。选项 B 把负担转移给开发者，却不改善系统。选项 C 误解了问题：更大的上下文窗口并不能解决注意力质量问题。选项 D 反而会压制对真实 bug 的检出，因为它要求对可能只是间歇性被发现的问题达成共识。
