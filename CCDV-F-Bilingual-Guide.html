Introduction

The Claude Certified Developer – Foundations certification validates that an individual can build, integrate, and ship production-grade applications, agents, and workflows using Anthropic's Claude platform at a foundational level. It is intended for technical professionals who bridge Claude's capabilities and production-ready applications, translating technical requirements into working systems through API integration, agent and tool construction, prompt and context engineering, evaluation, security, and model selection.

This guide is the study companion to the official Exam Guide, which is the authoritative reference for the credential: its purpose, intended audience, exam format and content blueprint, scoring, and policies.

Target Candidate

The certification is intended for technical professionals who build, integrate, and ship production-grade AI solutions using large language models (LLMs), particularly Anthropic's Claude platform — primarily AI and machine learning engineers, technical leads, and senior software engineers operating at the intersection of business requirements and technical implementation.

The exam targets the minimally qualified candidate (MQC): a hands-on technical individual who builds, integrates, and ships Claude-powered applications, agents, and workflows, translating technical requirements into working applications. Recommended experience (recommended, not required — there are no mandatory prerequisites):

  • One to five years of experience in software engineering
  • At least six months of hands-on experience with Claude or comparable LLM-based systems
  • Proficiency in Python and/or TypeScript
  • Fluency with REST APIs and CLI tools
  • Working understanding of LLM fundamentals, agents, context management, and MCP

1.1 Agent Architecture (4.5%)

Principles, patterns, and tradeoffs of agent and workflow architecture, including the decision criteria for using a workflow versus an agent, the structure of manager/supervisor hierarchies, and the role of subagents in improving task execution.

Official wording: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. … Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • The foundational distinction is control flow: in a workflow, LLMs and tools are orchestrated through predefined code paths; in an agent, the LLM dynamically directs its own process and tool usage. The decision criterion is predictability — if the steps can be specified in advance, a workflow is simpler, cheaper, and easier to verify; an agent earns its cost and risk only when the path cannot be predetermined.
  • Anthropic's guidance is to find the simplest solution possible and only increase complexity when it demonstrably improves outcomes: a single augmented-LLM call, then a workflow, then an agent, in that order of preference.
  • Manager/supervisor hierarchies (orchestrator-workers, lead agent with subagents) decompose a task under one coordinating agent: the manager plans, delegates self-contained subtasks, and synthesizes results. Subagents improve execution through parallel exploration and context isolation — each works in its own context window and returns a distilled result instead of raw intermediate work.
  • Agentic systems trade latency and cost for task performance, and add failure modes a workflow does not have: compounding errors across self-directed steps, harder debugging, and the need for sandbox testing, guardrails, and explicit stopping conditions.

Key skills:

  • Given a scenario, apply the workflow-versus-agent test: predictable steps → workflow; open-ended, environment-driven steps → agent — and name the deciding feature in the stem.
  • Sketch a supervisor hierarchy for a multi-part task: what the manager keeps, what it delegates, and what each subagent returns.

Official sources: Building effective agents · How we built our multi-agent research system

1.1 智能体架构（4.5%）

EN: Principles, patterns, and tradeoffs of agent and workflow architecture, including the decision criteria for using a workflow versus an agent, the structure of manager/supervisor hierarchies, and the role of subagents in improving task execution.

官方原文： "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. … Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

关键知识：

  • 根本区分在于控制流：在工作流（workflow）中，LLM 与工具通过预定义的代码路径编排；在智能体（agent）中，LLM 动态主导自身流程与工具使用。决策标准是可预测性 —— 如果步骤可以预先指定，工作流更简单、更便宜、更容易验证；只有当路径无法预先确定时，智能体的成本与风险才值得。
  • Anthropic 的指引是找到尽可能简单的方案，只在能明显改善结果时才增加复杂度：优先顺序是单次增强型 LLM（augmented LLM）调用、然后工作流、最后才是智能体。
  • 管理者/监督者层级（编排者-工作者、带子智能体的主智能体）在一个协调智能体之下分解任务：管理者负责规划、委派自包含的子任务并综合结果。子智能体（subagents）通过并行探索与上下文隔离改善执行 —— 每个子智能体在自己的上下文窗口中工作，返回提炼过的结果，而不是原始的中间工作。
  • 智能体系统以延迟和成本换取任务表现，并带来工作流没有的失败模式：自导步骤间的错误累积、更难的调试，以及对沙箱测试、护栏（guardrails）与明确停止条件的需求。

关键技能：

  • 给定一个场景，运用工作流与智能体的判断测试：步骤可预测 → 工作流；开放式、由环境驱动的步骤 → 智能体 —— 并说出题干中的决定性特征。
  • 为一个多部分任务画出监督者层级：管理者保留什么、委派什么、每个子智能体返回什么。

官方来源： 构建有效的智能体（Building effective agents） · 我们如何构建多智能体研究系统（How we built our multi-agent research system）

1.2 Agent Construction with Claude (5.3%)

Methods, tools, and platforms for constructing Claude agents, including the Claude Agent SDK, custom agent loops and harnesses, managed agent deployment models (self-hosted vs. Anthropic-hosted), and hooks for deterministic actions.

Official wording: "The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript." — Agent SDK overview, Anthropic (https://platform.claude.com/docs/en/agent-sdk/overview)

Key knowledge:

  • The Claude Agent SDK packages the Claude Code agent loop as a library for Python and TypeScript: built-in tools (read, write, edit files, run commands, search the web), hooks, subagents, MCP connections, permissions, and sessions are all available programmatically. An agent built on it is an application that plans its own steps and calls tools to complete a task.
  • A custom agent loop is the alternative: your code calls the Messages API, executes the tool calls Claude requests, returns tool_result blocks, and repeats until a stop condition. You own the loop's control flow, state, and error handling — more work, more control.
  • Deployment models split by who runs the harness: self-hosted (you run the Agent SDK or your own loop in your infrastructure) versus Anthropic-hosted Managed Agents (a hosted agent harness runs the loop, with sessions in an Anthropic-managed cloud sandbox or a self-hosted sandbox on your infrastructure, driven via SDK, the ant CLI, or the REST API).
  • Hooks are the deterministic layer inside an otherwise probabilistic system: user-defined code that runs automatically at lifecycle points (for example before a tool call executes) and can inspect, modify, or block actions — the mechanism for enforcing rules that must hold every time rather than relying on the model to comply.

Key skills:

  • Choose the construction method from the stem's constraints: fastest path to a working agent → Agent SDK; unusual control-flow or embedding requirements → custom loop; no infrastructure to run → Managed Agents.
  • Identify where a requirement ("this action must always be checked first") belongs: in a hook or permission rule, not in the system prompt.

Official sources: Agent SDK overview · Hooks reference — Claude Code

1.2 用 Claude 构建智能体（5.3%）

EN: Methods, tools, and platforms for constructing Claude agents, including the Claude Agent SDK, custom agent loops and harnesses, managed agent deployment models (self-hosted vs. Anthropic-hosted), and hooks for deterministic actions.

官方原文： "The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript." — Agent SDK overview, Anthropic (https://platform.claude.com/docs/en/agent-sdk/overview)

关键知识：

  • Claude Agent SDK 把 Claude Code 的智能体循环打包成 Python 与 TypeScript 的库：内置工具（读、写、编辑文件，运行命令，搜索网络）、hooks、子智能体、MCP 连接、权限与会话，全部可编程调用。用它构建的智能体是一个能规划自身步骤、调用工具完成任务的应用。
  • 自定义智能体循环（custom agent loop）是另一种选择：你的代码调用 Messages API，执行 Claude 请求的工具调用，返回 tool_result 块，如此重复直到停止条件。循环的控制流、状态与错误处理都归你所有 —— 工作更多，控制也更多。
  • 部署模型按谁来运行框架（harness）划分：自托管（self-hosted）（你在自己的基础设施里运行 Agent SDK 或自己的循环）与 Anthropic 托管的 Managed Agents（一个托管的智能体框架运行循环，会话位于 Anthropic 管理的云沙箱、或你自己基础设施上的自托管沙箱，通过 SDK、ant CLI 或 REST API 驱动）。
  • Hooks 是这个概率系统内部的确定性层：用户定义的代码在生命周期节点（例如工具调用执行之前）自动运行，可以检查、修改或阻止动作 —— 它是强制执行「每次都必须成立」的规则的机制，而不是依赖模型自觉遵守。

关键技能：

  • 从题干的约束出发选择构建方法：最快得到可工作的智能体 → Agent SDK；不寻常的控制流或嵌入需求 → 自定义循环；没有可运行的基础设施 → Managed Agents。
  • 判断一条需求（「这个动作必须总是先被检查」）属于哪里：属于 hook 或权限规则，而不是系统提示。

1.3 Agent Patterns and Frameworks (4.9%)

Common agent design patterns (tool-use loops, sub-agents, memory, context-window management) and agentic abstraction frameworks (e.g., Strands, LangGraph, PydanticAI) for building agents and workflows for multi-step tasks.

Official wording: "Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

Key knowledge:

  • The core pattern inventory: the tool-use loop (model requests a tool, harness executes it, result returns, repeat until done), prompt chaining and the other workflow patterns (routing, parallelization, orchestrator-workers, evaluator-optimizer), sub-agents for delegated subtasks, memory (information carried across steps or sessions, from conversation history to external stores), and context-window management (curating, pruning, and compacting what the model sees).
  • Patterns compose: a chained workflow can contain a tool-use loop at one step; an orchestrator can give each worker its own memory and context budget. The exam tests whether you can name the pattern a scenario describes and spot the one that does not fit.
  • Agentic frameworks (Strands, LangGraph, PydanticAI, and similar) are abstraction layers over the same primitives — loops, tool dispatch, state, and orchestration graphs. They trade the transparency and control of a hand-written loop for speed of construction and built-in structure; Anthropic's guidance is to understand what the framework does on your behalf before adopting it, because hidden prompt and control-flow abstractions make debugging harder.
  • Framework or not, the underlying mechanics are identical: messages, tool definitions and results, stop conditions, and context contents are what actually determine behavior.

Key skills:

  • Map a described system to its pattern (fixed sequence → chaining; classification front door → routing; generate-then-critique → evaluator-optimizer; delegated parallel exploration → sub-agents).
  • State the trade-off when a stem offers a framework versus a hand-rolled loop: construction speed and structure versus visibility and control.

1.3 智能体模式与框架（4.9%）

EN: Common agent design patterns (tool-use loops, sub-agents, memory, context-window management) and agentic abstraction frameworks (e.g., Strands, LangGraph, PydanticAI) for building agents and workflows for multi-step tasks.

官方原文： "Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one." — Building effective agents, Anthropic (https://www.anthropic.com/research/building-effective-agents)

关键知识：

  • 核心模式清单：工具使用循环（tool-use loop）（模型请求工具、框架执行、结果返回、重复直至完成）、提示链（prompt chaining）与其他工作流模式（路由、并行化、编排者-工作者、评估者-优化者）、用于委派子任务的子智能体（sub-agents）、记忆（memory）（跨步骤或跨会话携带的信息，从对话历史到外部存储），以及上下文窗口管理（策展、修剪与压缩模型所见的内容）。
  • 模式可以组合：一个链式工作流可以在某一步包含工具使用循环；一个编排者可以给每个工作者各自的记忆与上下文预算。考试考的是你能否说出场景所描述的模式，并识别出不合適的那一个。
  • 智能体框架（Strands、LangGraph、PydanticAI 等）是同一批原语之上的抽象层 —— 循环、工具分发、状态与编排图。它们以手写循环的透明性与控制力换取构建速度与内置结构；Anthropic 的指引是：在采用框架之前先理解它替你做了什么，因为隐藏的提示与控制流抽象会让调试更难。
  • 无论是否用框架，底层机制都相同：消息、工具定义与结果、停止条件与上下文内容，才是实际决定行为的东西。

关键技能：

  • 把描述中的系统映射到它的模式（固定序列 → 链式；分类前门 → 路由；先生成后批评 → 评估者-优化者；委派并行探索 → 子智能体）。
  • 当题干在框架与手写循环之间给出选择时，说清权衡：构建速度与结构，对比可见性与控制力。

2.1 Understanding Requirements (3.4%)

Functional and infrastructure requirements based on business requirements and solution architecture.

Official wording: "They bridge Claude's capabilities and production-ready applications, translating technical requirements into working applications." — Claude Certified Developer – Foundations Exam Guide v1.0, Anthropic

Key knowledge:

  • Requirements work splits into functional requirements (what the system must do: tasks, inputs and outputs, accuracy and quality bars, which tools and data it needs) and infrastructure requirements (how it must run: latency, throughput, cost ceiling, data residency and privacy, availability, integration points with existing systems).
  • Both derive from the business requirement and the solution architecture, not from the model's capabilities: a Claude application is designed backwards from the job, the constraints, and the success criteria that will be measured.
  • Requirements decide downstream choices before any code exists: real-time versus batch processing, which model tier, whether tools are needed at all, and what evaluation will prove the system works. Vague requirements ("make it smart") are a defect to fix in discovery, not a prompt problem.
  • The candidate profile in the Exam Guide frames the developer's role exactly this way: bridging Claude's capabilities and production-ready applications, translating technical requirements into working applications at the intersection of business requirements and technical implementation.

Key skills:

  • Restate a business ask as functional requirements (task, inputs, outputs, quality bar) plus infrastructure requirements (latency, volume, cost, privacy) before proposing an implementation.
  • Spot the missing requirement in a scenario stem — the unstated latency, volume, or compliance constraint that changes the correct design.

Official sources: Claude Certified Developer – Foundations Exam Guide v1.0, Sections 3–4, Anthropic

2.1 理解需求（3.4%）

EN: Functional and infrastructure requirements based on business requirements and solution architecture.

官方原文： "They bridge Claude's capabilities and production-ready applications, translating technical requirements into working applications." — Claude Certified Developer – Foundations Exam Guide v1.0, Anthropic

关键知识：

  • 需求工作分为功能需求（系统必须做什么：任务、输入与输出、准确性与质量标准、需要哪些工具与数据）与基础设施需求（系统必须如何运行：延迟、吞吐量、成本上限、数据驻留与隐私、可用性、与既有系统的集成点）。
  • 两者都源自业务需求与解决方案架构，而不是模型的能力：Claude 应用是从工作本身、约束条件与将被度量的成功标准倒推设计的。
  • 需求在任何代码存在之前就决定了下游选择：实时处理还是批处理、用哪个模型层级、到底需不需要工具、以及用什么评估来证明系统有效。含糊的需求（「让它变聪明点」）是发现阶段要修的缺陷，不是提示问题。

2.3 Claude API Mechanics (6.8%)

Claude API behavior and mechanics, including messages, tools, streaming, vision, thinking, caching, invoking Claude through third-party vendors, Messages API data access patterns, batch API use, and tradeoffs between realtime and batch API selection.

Official wording: "Prompt caching covers the full prefix: tools, system, and messages (in that order), up to and including the block designated with cache_control." — Prompt caching, Anthropic (https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Key knowledge:

  • The Messages API is the core interface: you send a model, a system prompt, and a list of messages (user/assistant turns made of content blocks — text, images, documents, tool_use, tool_result), plus parameters such as max_tokens; the response returns content blocks and a stop_reason that tells you why generation ended (end of turn, tool use, token limit, refusal).
  • Tool use runs through the API: you declare tools with names, descriptions, and JSON input schemas; Claude responds with a tool_use block; your code executes the tool and returns a tool_result block; the loop repeats. Streaming delivers the response incrementally as server-sent events for lower time-to-first-token in interactive applications. Vision passes images and documents as content blocks alongside text.
  • Thinking gives Claude internal reasoning tokens before (and between) answers — adaptive thinking lets the model decide how much to think, controlled by effort levels — and prompt caching reuses a stable prompt prefix (tools, system, messages, in that order) across requests to cut cost and latency, with 5-minute or 1-hour cache lifetimes.
  • The Message Batches API is the asynchronous counterpart: large workloads are submitted as a batch, processed within a 24-hour window, at 50% of standard token prices. The realtime-versus-batch tradeoff is the exam's favorite in this domain: interactive or deadline-tight work stays synchronous; latency-tolerant, high-volume, cost-sensitive work (overnight jobs, bulk classification) goes to batches. Claude can also be invoked through third-party vendors (Amazon Bedrock, Google Cloud, Microsoft Foundry), where the same Messages API patterns apply under the vendor's platform.

Key skills:

  • Read a scenario's latency and volume cues and select synchronous Messages API versus Message Batches — overnight, non-urgent, cost-first means batch.
  • Identify the mechanical fix for a described symptom: repeated static prefix billed every request → prompt caching; user staring at a spinner → streaming; multi-step external actions → the tool-use loop.

4.1 Debugging and Error Handling (2.6%)

Debugging and error handling techniques for Claude applications, including error type identification, recovery strategy selection, trace analysis to identify failure modes, and problem origin isolation between the integration layer and model output.

Official wording: "When Claude ignores an instruction or a feature you configured doesn't appear, the cause is usually that the file didn't load, it loaded from a different location than you expected, or another file overrode it." — Debug your configuration, Anthropic (https://code.claude.com/docs/en/debug-your-config)

Key knowledge:

  • Debugging a Claude application starts with error type identification: API and transport errors (rate limits, overloads, invalid requests), configuration errors (a file that didn't load, loaded from the wrong place, or was overridden), and model-output errors (wrong format, wrong tool choice, hallucinated content) each have different fixes, and confusing them wastes the debugging session.
  • Problem origin isolation is the central skill: is the failure in the integration layer (your code, request construction, tool execution, configuration resolution) or in the model output (prompt quality, missing context, model capability)? Configuration surprises in Claude Code are usually resolution problems — not loaded, wrong location, overridden — not model problems, and the same suspicion order applies to API applications.
  • Trace analysis reads the record of what actually happened — requests, tool calls, tool results, stop reasons, token usage — to find the step where behavior diverged, instead of guessing from the final output. In structured outputs, for example, a stop_reason of "refusal" or "max_tokens" explains an off-schema response that looks like a model failure but is neither.
  • Recovery strategy selection follows the diagnosis: retry with backoff for transient API errors, fix the configuration at the scope that actually wins for resolution problems, add validation and retry-with-feedback for output problems, and feed every recurring failure back into the eval set so it is tested forever after.

Key skills:

  • Triage in order: reproduce, inspect what actually loaded and what the trace shows, classify the error (transport, configuration, or model output), then fix at that layer.
  • Refuse the model-blaming distractor: when the stem shows a configuration or integration cause, the correct answer fixes the harness, not the prompt or the model.

5.1 LLM Fundamentals (5.2%)

Basic understanding of LLMs (tokens, context windows, sampling, non-determinism, next-token generation), model options (fast mode, extended thinking, adaptive thinking, effort levels), and fundamental prompting techniques (zero-shot, single-shot, multi-shot).

Official wording: "The "context window" refers to all the text a language model can reference when generating a response, including the response itself." — Context windows, Anthropic (https://platform.claude.com/docs/en/build-with-claude/context-windows)

Key knowledge:

  • An LLM generates text one token at a time by predicting the next token; everything it can condition on lives in the context window — the system prompt, all messages, tool definitions and results, and the response itself all count toward it. More context is not automatically better: as token count grows, accuracy and recall degrade (context rot).
  • Sampling makes generation probabilistic: the model picks among likely next tokens, so identical inputs can produce different outputs — non-determinism is a property of the system, and applications that need consistency get it from structure, validation, and evals, not from expecting identical replies.
  • Model options tune the reasoning budget: extended thinking gives Claude internal reasoning tokens; adaptive thinking lets the model decide how much to think, steered by effort levels; fast mode trades cost for lower latency on supported models. Thinking tokens are billed as output tokens and count toward the context window.
  • Fundamental prompting techniques form a ladder: zero-shot (instruction only), single-shot (one example), and multi-shot / few-shot (several examples) — examples are added when instructions alone do not pin down the format or behavior.

Key skills:

  • Explain a symptom from first principles: inconsistent answers across identical calls → sampling non-determinism; degraded quality in a very long session → context rot and window pressure.
  • Pick the reasoning configuration from the task: routine extraction → low effort or thinking off; multi-step reasoning → adaptive thinking at higher effort.

5.2 Technical Fundamentals (6.1%)

Foundational technical concepts supporting AI application development, including basic engineering practices (integrating with SDKs that wrap REST APIs, websockets).

Official wording: "When creating a Message, you can set "stream": true to incrementally stream the response using server-sent events (SSE)." — Streaming messages, Anthropic (https://platform.claude.com/docs/en/build-with-claude/streaming)

Key knowledge:

  • The Claude API is a REST API; the official client SDKs wrap it, handling request construction, authentication, retries, and response parsing in Python, TypeScript, and other languages — you integrate with the SDK's types and helpers rather than hand-building HTTP calls.

Key skills:

  • Choose the consumption pattern a scenario needs: full response for short calls, SSE streaming for interactive output, asynchronous batch submission for bulk work.
  • Build the client defensively: accumulate streamed deltas, handle mid-stream error events, and retry transient failures with backoff.

5.4 Cost and Token Management (2.8%)

Token budgeting and cost management techniques for Claude applications, including token usage tracking, cost modeling, and caching techniques (prompt caching, cache check-pointing) for cost optimization.

Official wording: "Prompt caching optimizes your API usage by letting the API resume from specific prefixes in your prompts. This significantly reduces processing time and costs for repetitive tasks or prompts with consistent elements." — Prompt caching, Anthropic (https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Key knowledge:

  • Cost is tokens times price, so management starts with tracking: every response reports its consumption in the usage field (input, output, cache creation, and cache read tokens), and the token counting API estimates a request before you send it. A cost model multiplies expected token volumes by per-model prices to forecast spend per feature or per task.
  • Token budgeting caps the downside: max_tokens bounds output, effort levels bound thinking spend, and context discipline (pruning tool results, compacting history) bounds input growth across a long session or agent loop.
  • Prompt caching is the biggest lever for repeated prefixes: content up to a cache_control breakpoint — covering tools, system, and messages in that order — is written once (at a premium over base input price) and read back at a fraction of it, with a 5-minute lifetime refreshed on use or a 1-hour option. Cache check-pointing in long conversations (automatic caching) moves the breakpoint forward as the conversation grows, so each turn re-reads the accumulated history from cache.
  • Caching has failure modes a budget owner must know: changing anything at or before the breakpoint invalidates the prefix, breakpoints placed on per-request content never hit, and cached prefixes still occupy the context window — caching changes what you pay, not what counts.

Key skills:

  • Build a rough cost model from a scenario: requests × (input + output tokens) × tier price, then name the lever that reduces it (caching, batch, tier routing, effort).
  • Place cache breakpoints correctly: at the end of the static prefix (tools, system, stable context), never on the varying per-request block.

5.4 成本与 Token 管理（2.8%）

关键知识：

  • 成本等于 token 乘以价格，因此管理从追踪开始：每个响应都在 usage 字段报告其消耗（输入、输出、缓存创建与缓存读取 token），而 token 计数 API 在你发送前估算一个请求。成本模型把预期的 token 量乘以各模型的价格，预测每个功能或每个任务的花费。

  • 正确放置缓存断点：在静态前缀的末尾（工具、系统、稳定上下文），绝不放在每请求变化的块上。

6.1 Context Engineering (3.8%)

Context and memory management techniques for Claude applications, including context window management, prevention of context drift and bloat (tool output pruning, compaction), and context isolation through subagents or multi-step agentic workflows.

Official wording: "As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available." — Context windows, Anthropic (https://platform.claude.com/docs/en/build-with-claude/context-windows)

Key knowledge:

  • Context engineering is the discipline of curating what occupies the context window: the window is a finite working memory, everything in the request counts toward it, and quality degrades as it fills — so the goal is the smallest set of high-signal tokens that does the job, not the most data available.
  • Context bloat has named sources and named fixes: raw tool outputs are pruned to the fields the task needs (tool output pruning, tool result clearing), long conversations are summarized (compaction — server-side compaction automatically summarizes earlier parts of the conversation so it can continue past the limit), and stale instructions are removed before they conflict.
  • Context drift is the behavioral symptom: as sessions lengthen and accumulate off-task or contradictory material, the model's adherence to the original instructions decays. Session hygiene — fresh sessions for new tasks, deliberate pruning, compaction at the right moment — is the prevention.
  • Context isolation keeps one task's noise out of another's: subagents work in their own context windows and return distilled results, and multi-step agentic workflows pass structured state between steps instead of one ever-growing transcript.

Key skills:

  • Diagnose drift and bloat from a stem (long session, huge tool results, fading instruction adherence) and prescribe the matching fix: prune, compact, or isolate.
  • Decide what survives compaction: the facts, decisions, and state the next step needs — not the raw transcript.

Official sources: Context windows

6.2 Prompt Engineering (4.6%)

Official wording: "Examples are one of the most reliable ways to steer Claude's output format, tone, and structure. Key knowledge:

  • Instruction clarity is the first principle: be clear, direct, and specific about the output you want, with context and motivation for why — the official test is whether a colleague with minimal context could follow the prompt without confusion. Vague instructions get inferred behavior; explicit criteria get followed behavior.
  • Placement is structural: stable instructions and role belong in the system prompt; the task and variable input belong in user messages; examples steer format, tone, and structure and should be relevant, diverse, and structured (wrapped in <example> tags); XML tags separate instructions, context, and input in complex prompts; long documents go at the top, above the query.
  • Output constraints are stated positively and concretely — tell Claude what to do instead of what not to do, specify format and length, and match the prompt's own style to the output style you want.
  • Iteration is the method: prompt changes are hypotheses tested against examples and evals — adjust one thing, re-measure, keep what improves. Input sanitization belongs to the prompt layer too: untrusted input is delimited, encoded, and kept separate from instructions so it cannot blend into them.

Key skills:

  • Rewrite a vague prompt into a clear one: role in system, task and input delimited in the user turn, explicit output format, and a few-shot example when format consistency matters.
  • Choose the lightest fix that matches the failure: unclear instruction → clarify; format drift → examples or structured outputs; inconsistent behavior across components → fix placement, not wording.

6.3 Output Handling (2.6%)

Official wording: "Without structured outputs, Claude can generate malformed JSON responses or invalid tool inputs that break your applications." — Structured outputs, Anthropic (https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

Key knowledge:

  • The reliable pattern is to make output machine-checkable at the source: structured outputs constrain responses to a JSON schema through constrained decoding (always valid, type safe, no retries needed for schema violations), and strict tool use does the same for tool inputs.

  • Skepticism toward confident output is an explicit design stance: fluent, confident text is not evidence of correctness. High-stakes output gets verified — grounded against sources, checked by a second pass or a human — before it is consumed or acted on.

Key skills:

  • Pick the output strategy by consumer: another program → structured outputs or strict tool use; a human reader → prose with validation of any extracted fields.
  • Handle the two off-schema cases by stop reason: refusal → surface or reroute, never parse; max_tokens → retry with a higher limit.

7.1 AI Application Security (3.2%)

Data privacy and security best practices, including prompt injection awareness and mitigation, jailbreak defense, untrusted input handling, data leakage prevention, PII handling, and ensuring authentication, authorization, confidentiality, privacy, and integrity.

Official wording: "Tell Claude explicitly that content returned from tools, documents, or searches is untrusted data and must never override the system prompt or the user's original request." — Mitigate jailbreaks and prompt injections, Anthropic (https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)

Key knowledge:

  • Prompt injection comes in two threat models: direct injection and jailbreaks, where the user is the adversary; and indirect injection, where a trusted user asks Claude to process third-party content (webpages, emails, documents, tool results) that contains adversarial instructions. The mitigations differ, and the exam tests which one a scenario describes.

Key skills:

  • Classify the attack in the stem (malicious user → direct; poisoned document or tool result → indirect) and select the mitigation set for that threat model.
  • Reject the non-controls: raising temperature, asking users politely in the system prompt, or switching to a more instruction-following model — the last can make injection worse, not better.

7.3 Claude Hooks (1.0%)

Key knowledge:

  • A hook is deterministic code — a shell command, HTTP endpoint, MCP tool call, LLM prompt, or subagent — that Claude Code runs automatically when a lifecycle event fires and a matcher matches. Key skills:

  • Convert a safety requirement into a hook design: event (PreToolUse), matcher (the tool or command pattern), handler decision (deny with a reason the model can act on).

  • Identity validation is enforceable in configuration: managed settings can require a specific login method (forceLoginMethod) and restrict logins to a specific organization (forceLoginOrgUUID), and can restrict which API providers a machine may use — access approval and level verification are settings, not conventions.

  • Authorized access monitoring closes the loop: authentication events and usage are auditable (who signed in, with which credential type, from which organization), and unexpected credential use is a signal to investigate, not a curiosity.

Key skills:

  • Pick the credential for the environment: interactive developer → OAuth login/profile; application server → API key in an environment variable or secret store; regulated organization → managed settings enforcing login method and organization.
  • Respond to a suspected key leak in the right order: revoke/rotate the key first, then investigate usage — not the reverse.

8.1 Tool Implementation (4.4%)

Tool implementation practices for Claude applications, including tool use and function calling, configuration for external system interaction, tool description writing, error handling, tool usage patterns (agentic harness dispatch, client-side vs. server-side tools, approval patterns), and tool set construction best practices.

Official wording: "Tools are a new kind of software which reflects a contract between deterministic systems and non-deterministic agents. More tools don't always lead to better outcomes." — Writing effective tools for AI agents, Anthropic (https://www.anthropic.com/research/writing-tools-for-agents)

Key knowledge:

  • A tool is a contract: a name, a description, and a JSON input schema that your code implements and Claude invokes through tool_use blocks. The agentic harness dispatches each call, executes it, and returns the tool_result; Claude never executes anything itself. Client-side tools run in your application; server-side tools (such as web search and code execution) run on Anthropic's infrastructure.
  • Tool descriptions are the interface: because the model chooses tools from their descriptions, a description must say what the tool does, when to use it, and what it returns — written for a reader who cannot see your code. Vague descriptions and overlapping tools are the leading cause of wrong-tool and wrong-argument failures.
  • Tool set construction is deliberately minimal: consolidate operations the agent needs into a small set of high-level tools rather than exposing every low-level API endpoint, return only the information the next decision needs, and remember that more tools do not always lead to better outcomes — every tool definition also consumes context.
  • Error handling and approval patterns are part of the tool, not an afterthought: return structured, actionable errors the model can recover from (what failed, what to change), and put consequential actions behind approval — permission rules or hooks that ask a human before the call executes.

Key skills:

  • Rewrite a failing tool: sharpen the description, narrow or consolidate the schema, and trim the result payload — before touching the prompt or the model.
  • Decide where a tool runs and what gates it: server-side built-in, client-side custom, or client-side behind an approval pattern, based on where the system it touches lives.

Official sources: Writing effective tools for AI agents · Structured outputs

8.1 工具实现（4.4%）

EN: Tool implementation practices for Claude applications, including tool use and function calling, configuration for external system interaction, tool description writing, error handling, tool usage patterns (agentic harness dispatch, client-side vs. server-side tools, approval patterns), and tool set construction best practices.

官方原文： "Tools are a new kind of software which reflects a contract between deterministic systems and non-deterministic agents. More tools don't always lead to better outcomes." — Writing effective tools for AI agents, Anthropic (https://www.anthropic.com/research/writing-tools-for-agents)

关键知识：

  • 工具是一份契约：一个名称、一段描述与一个 JSON 输入架构，由你的代码实现、由 Claude 通过 tool_use 块调用。智能体框架（agentic harness）分发每个调用、执行它并返回 tool_result；Claude 自己从不执行任何东西。客户端工具在你的应用中运行；服务器端工具（如网络搜索与代码执行）在 Anthropic 的基础设施上运行。
  • 工具描述就是接口：因为模型是根据描述来选择工具的，一段描述必须说明工具做什么、何时使用、返回什么 —— 为一个看不到你代码的读者而写。含糊的描述与重叠的工具是选错工具与传错参数失败的首要原因。

关键技能：

  • 重写一个失败的工具：磨利描述、收窄或整合架构、修剪结果负载 —— 在动提示或模型之前先做这些。
  • 决定一个工具在哪里运行、由什么把关：服务器端内置、客户端自定义，或客户端加批准模式 —— 依据它所触及的系统住在哪里。

8.2 MCP Server Development (2.1%)

MCP server development practices, including server authoring, deployment, integration with Claude applications, MCP resources, tools, and prompts, and communication patterns (stdio, sockets, client vs. server).

Official wording: "MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems." — What is the Model Context Protocol (MCP)?, Model Context Protocol (https://modelcontextprotocol.io/docs/getting-started/intro)

Key knowledge:

  • The Model Context Protocol standardizes how AI applications connect to external systems — data sources, tools, and workflows — the way USB-C standardizes device connections. An MCP server exposes capabilities once, and any MCP client (Claude applications, Claude Code, IDEs) can connect to it, which is what makes the capability reusable across applications and maintainable independently of any one app.
  • A server exposes three primitive types: tools (functions Claude can invoke), resources (data the application can read into context), and prompts (reusable prompt templates). Authoring a server means implementing these primitives with the same description-and-schema discipline as any tool.
  • Communication patterns split by deployment: stdio transport, where the client launches the server as a local subprocess and talks over standard input/output — the default for local tools; and HTTP/sockets-based transports for remote servers that many clients share. The client-versus-server roles are fixed by the protocol: the client hosts the model interaction and connects out; the server only exposes capabilities.
  • Integration with Claude applications can also skip a local client: the Messages API's MCP connector connects to remote MCP servers directly, without a separate MCP client in your code.

Key skills:

  • Choose the transport from the deployment: local developer tool → stdio server; shared internal service for several applications → remote server over HTTP.
  • Recognize the MCP answer in a stem: "reusable across applications, maintained independently" is the protocol's reason to exist — build the server, don't hard-code the integration into each app.

Official sources: What is the Model Context Protocol (MCP)?

8.3 Agentic Customization (4.1%)

Tradeoffs among built-in Tools, custom Tools, Skills, and MCPs for selecting and applying the appropriate approach for a given use case.

Official wording: "Skills are reusable, filesystem-based resources that give Claude domain-specific expertise: workflows, context, and best practices that turn a general-purpose agent into a specialist." — Agent Skills, Anthropic (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)

Key knowledge:

  • Four customization mechanisms, four different jobs. Built-in tools are Anthropic's ready-made capabilities (file operations, bash, web search, code execution): zero construction cost, fixed behavior. Custom tools are your functions behind the tool-use contract: full control, your maintenance burden, scoped to the application that defines them.
  • Skills package expertise rather than actions: instructions, workflows, and reference material on the filesystem, loaded by progressive disclosure — only the name and description occupy context until the Skill triggers, then its instructions load, then bundled resources and scripts load as needed. A Skill teaches Claude how to do a class of work; it is created once and used automatically across conversations.
  • MCPs package connectivity rather than expertise: a server exposes tools/resources/prompts over the protocol so many applications can share one maintained integration. The same capability can legitimately exist at several layers — the exam asks which layer the stem's requirement (reuse across apps? procedural know-how? a single function call?) actually points to.
  • The tradeoffs in one line each: built-in = fastest, least control; custom tool = one action, one app; Skill = reusable know-how with near-zero idle context cost; MCP = reusable connectivity across applications and teams, at the cost of running and securing a server.

Key skills:

  • Classify the requirement before choosing: "Claude must call our inventory API" → tool or MCP; "Claude must follow our review procedure" → Skill; "every team's apps need the same integration" → MCP; "just read and edit files" → built-in tools.
  • Argue the context economics: prefer the mechanism whose idle cost matches its use frequency — progressive-disclosure Skills for occasionally needed expertise, always-loaded tool definitions only for constantly used actions.

8.3 智能体定制（4.1%）

EN: Tradeoffs among built-in Tools, custom Tools, Skills, and MCPs for selecting and applying the appropriate approach for a given use case.

官方原文： "Skills are reusable, filesystem-based resources that give Claude domain-specific expertise: workflows, context, and best practices that turn a general-purpose agent into a specialist." — Agent Skills, Anthropic (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)

关键知识：

  • 四种定制机制，四种不同的工作。内置工具（built-in tools）是 Anthropic 现成的能力（文件操作、bash、网络搜索、代码执行）：零构建成本、行为固定。自定义工具（custom tools）是工具使用契约背后的你的函数：完全控制、你的维护负担、作用域限于定义它的应用。
  • Skills 打包的是专长而不是动作：文件系统上的指令、工作流与参考材料，通过渐进披露（progressive disclosure）加载 —— 直到 Skill 触发前只有名称与描述占据上下文，然后它的指令加载，再然后打包的资源与脚本按需加载。一个 Skill 教 Claude 如何做一类工作；它创建一次，便跨对话自动使用。
  • MCP 打包的是连接性而不是专长：一个服务器通过协议暴露工具/资源/提示，使许多应用能共享一份被维护的集成。同一个能力可以合理地存在于多个层 —— 考试问的是题干的需求（跨应用复用？程序性诀窍？单个函数调用？）实际指向哪一层。
  • 每种权衡用一句话说：内置 = 最快、控制最少；自定义工具 = 一个动作、一个应用；Skill = 可复用的诀窍，闲置上下文成本近乎零；MCP = 跨应用与团队的可复用连接性，代价是运行并保护一个服务器。

关键技能：

  • 先给需求分类再选择：「Claude 必须调用我们的库存 API」→ 工具或 MCP；「Claude 必须遵循我们的审查程序」→ Skill；「每个团队的应用都需要同一个集成」→ MCP；「只是读写文件」→ 内置工具。
  • 论证上下文经济学：优先选择闲置成本与使用频率相匹配的机制 —— 偶尔需要的专长用渐进披露的 Skills，常开加载的工具定义只留给持续使用的动作。

Sample 2 · Domain 7 — Security and Safety

A Claude-powered agent summarizes web pages submitted by end users. One page contains hidden text instructing the model to ignore previous instructions and reveal its system prompt. Which mitigation is most effective?

  • A. Raise the model's temperature so its behavior is harder to predict.
  • B. Treat retrieved page content as untrusted input, keep it separate from trusted instructions, and use guardrails or hooks so injected instructions cannot trigger sensitive actions.
  • C. Add a line to the system prompt asking users not to include malicious instructions.
  • D. Switch to a larger model that follows instructions more reliably.
